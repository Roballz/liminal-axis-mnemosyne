更新：2026-09-23。状态：第1节为用户已确认需求；第2节为固定源码事实；第3～6节的字段、默认值和实施方式为 proposed。只改文档，未编写实现、运行项目测试、调用用户模型或操作手机。不是任务卡。

阶段入口：`../stages/S-daily-baibai-mvp.md`。事件规则：`14-event-chain-mvp-proposal.md`。本文与14更新取代旧“先检索6～10张候选事件卡、自动覆写全链短概述、事件只能随摘要调用”的建议；旧方案保留在Git历史，不重新作为前置。

## 1. 已确认需求

- 本机IndexedDB可迁移库、直接沿用用户柏宝书分支及前端、保留已有混合召回和原文升级的选择不变。现用TT手机版+柏宝书流畅；旧Mnemosyne Demo的读写放大不是该模式的问题。
- 初版包含事件表及事件链召回。三项召回规则已确认：每链最多额外一条进展且避免和命中/近期正文重复；同链多命中共用一次事件包装；概述、进展、成员数和序号都服从同一分支/查询截止点。
- 给负责事件整理的AI提供当前合法范围内的全部事件链目录：稳定ID、标题、概述、状态、关键词等；不先检索6～10张候选卡。目录不是全库所有原文和成员摘要全文。
- 概述采用增量追加：AI只添加新发生内容，不改写过去概述。一批中同一事件涉及五条摘要时，保留五条摘要关联，只追加一到两句该批进展，不写五份重复概述。
- 增加独立事件LLM调用途径，可按用户设置每30或50楼等间隔整理一次；该调用专注事件，不承担摘要重写、物品/人物/变量重复更新。也需要手动补齐未整理范围的入口。
- 自定义表是明确产品需求：用户可按需要建表和字段，不受内置模板束缚；允许仅本地前端持久保存，不以远端同步为前置。最小首版范围和具体字段尚未全部冻结。

## 2. yuzuki-Memory：实际核对的机制

固定源码版本：`gaigai315/yuzuki-Memory@14ddb8df3207f5f8e0ac8af4c93b72edce00f704`。以下是源码判断，不是TT手机实测；用户对回溯页面体验的说明与源码事实分开。

### 2.1 总楼数、填表进度与自动触发

`config/task-runner.js`：

| 位置/函数 | 核对事实 |
| --- | --- |
| `getChatLength()` | 总量取当前`chat.length`；这是宿主聊天数组条目数，不是摘要条数或User+Assistant回合数 |
| `normalizePointers()` | 进度保存在`state.settings.manualPointers`，`trace`、`summary`、`historySummary`各自独立，并有各自postpone字段 |
| `buildAutoTraceTask()` | 批量填表启用时，`chatLength - pointers.trace >= interval + delay`且满足postpone后触发；interval取autoTraceBatchSize/traceBatchSize，回退40 |
| 同上 | 处理范围为`[lastIndex, min(lastIndex + interval, chatLength))`；延迟用于留下后续楼层，不是把整个积压范围一次塞进请求 |
| `runAutoTraceTask()` | 先生成/必要时确认，再应用结果和推进trace到本批end；保存失败恢复先前状态，不把失败批次当作完成 |
| `scheduleAutoSummary()` | 自动流程检查会话、前台生成和任务忙碌、最新assistant消息稳定性；不是看到数组长度增加便无条件并发执行 |

所以“记了多少楼”核心是程序维护的处理边界，不是AI自报，不是统计表格有几行。该指针不等于已经逐条证明全部历史内容完整：手动范围、旧楼修改、空洞等仍需要各自校验。

`chatMessagesFromRange()`按实际楼层范围取当前选中swipe文本，标注原始楼层，过滤插件消息等；实际发给AI的条目数可以少于数组范围长度。`buildTaskRangeText()`同时描述范围、总楼层和实际消息数。

本轮核对了任务层的范围/指针/自动提交路径，未逐项审阅872KB的整个`ui/memory-window.js`回溯弹窗与所有手动批次循环，不冒充完整UI验收。对于我们的“补齐剩余”入口，按下文明确规定快照、分批和恢复，不从界面描述臆造上游保证。

### 2.2 楼层变更与有效状态

`config/floor-ledger.js`把实时表格变更挂在消息`extra.yzm_memory_floor_delta`，记录ledgerId、entryId、swipe；账本另有signature、rows、floorScope等材料，当前表由基线和有效条目重放。signature包含消息角色、swipe、当前文本摘要和部分宿主信息。任务层另有删除后的指针/摘要范围对账。

值得借鉴的是“持久进度+来源标记+重放”，不是把楼层号或上游短hash直接当Mnemosyne永久身份，也不能据此宣称上游解决了所有深层edit/并发/跨设备情况。

### 2.3 表格与专用提示词

`task-runner.js`使用`state.tables`、`table.columns`与`state.records[tableId]`组织表定义和行值；能构建表结构提示词、现有表格参考以及限定目标表的更新限制。列名修饰符`#`表示追加、`*`表示仅填一次。

`buildTraceMessages()`仍会组合背景、世界书、现有表格、任务提示词，批量模式还可能附角色状态提示词。因此不能原样照搬整条任务调用并称它是“只做事件”的调用：我们的事件job必须使用事件专属输入/提示词和写入白名单。

`commitTraceResult()`没有有效写入时返回失败。我们的事件整理不应照搬这个条件：合法检查结果可能确实没有事件，必须区分“明确无事件”与“响应缺字段/解析失败”。

核对根目录未见许可证文件，仓库metadata的license为空；只据此标记直接复制代码前需确认授权，不作版权状态的最终法律判断。本轮仅借鉴机制，不复制其实现。

## 3. 我们的批量事件任务：建议

### 3.1 模式和输入

事件更新可选随摘要、独立批量、手动；这是建议的UI组织方式，默认推荐独立批量，具体默认间隔待试用。模式切换共享同一事件进度账本，同一输入不由两个主动写入者重复追加。现有摘要/状态流程继续工作，独立事件任务不重复结算这些状态。

独立事件调用只读取：目标故事/分支固定范围；本批正文及对应L0摘要/稳定ID；该批可用的全量事件目录；事件任务规则和必要输出约束。不要附带物品增减、角色状态、变量任务提示词，也不能让模型的额外字段越权写那些表。

增量任务使用批次之前的合法事件视图；之后批次读取前一批已提交目录。历史补录不能读取未来版本的事件标题、概述、状态等再伪装成当时已知内容；缺合法历史视图时显式处理，不混用最新表。旧来源不足仅能作为有声明参考，不伪造原文引用。

全量指作用域内所有允许发送的链，含结束/沉寂事件，不跨其他故事、不包含未来或禁发内容。请求前显示材料量并检查模型预算；超限提示缩小正文批次或用户处理目录，不能暗中退回候选检索、删旧概述或静默裁掉部分事件。全量目录本身已超预算时，只减正文批次无法解决，须明确报告。普通聊天/既有召回不因事件目录过大而全局不可用。

### 3.2 间隔、批量与进度

“每隔N楼触发”“每次最多处理多少楼/多长文本”“保留多少最新楼暂不处理”分成不同设置。30/50是用户例子，不宣称已定默认值。界面须明确计数单位；建议提供“聊天消息楼”和“AI回复/已有摘要条数”的明确标签，不把30楼自动当30轮。完整User+Assistant配对不能因批次边界被拆错，未完成回合留下一批。

程序保存实际处理的message/revision和memory/revision清单、固定范围/来源指纹、operation/job标识及结果状态；游标只是加速找下一批，不能仅用最大楼层号掩盖中间缺口。摘要完成度、事件完成度独立显示。

建议状态区分：未处理、已关联、已检查无事件、待确认、因版本变化待复核、失败。缺事件输出不等于无事件；明确无事件在成功保存检查回执后可完成，待确认单独展示、不假装已全部归档。重复请求恢复同一操作，不重复追加段落/ID。

一个批次的事件元信息/关联/追加概述/处理回执在同一数据库事务内发布；模型调用在事务外。保存失败不推进完成进度。并发新正文不盲目使固定旧批失效，但目标源版本、关联、人工锁定或事件视图已变时必须重核，不能覆盖新编辑。

手动“补齐剩余”固定本次目标上限，顺序分批成功后再执行下一批；支持停止和重开续跑，最后不足N楼也可手动补。应用关闭或手机暂停期间不承诺仍执行，重开后从持久回执继续。不会把用户本次确认自动扩大为未来所有私人历史或无限模型调用。

## 4. 追加概述与召回展示：建议分开

持久模型建议是事件元信息+独立的进展段+摘要关联。每个进展段保存稳定ID、事件ID、内容、实际摘要/原文版本引用、批次与生效范围。状态/标题/关键词可以按规则更新，概述正文仅追加；AI不重写旧段。修错走人工版本化修订/补充纠正，保留原记录，不能把“只追加”变成明知错误也永久强制注入。

一批五条摘要可关联一个进展段，但五个摘要ID都保留；概述条数不等于关联摘要数。若一个进展段只依据五条材料，显示为这五条的归组说明；如还读过额外上下文，实际input_refs不得漏记。

重要差别：多次追加后得到的是事件简史，不再永远是一到两句的全链短概述。不能把无限简史直接放进原有短概述槽，也不在后台偷偷覆写压缩。

推荐召回投影：命中内容+事件名/范围内序号+起始概述与命中所在批次概述的有界节选+至多一条最新有效进展，标明“事件概述节选”；同段只发一次，按预算可省略补充，完整简史留事件页。此具体投影还未获用户确认，不把它写成已冻结；另一种新建可重建短总览也必须单独明确授权，不替代追加原文。

若一段概述依据#10、#20、#30，而查询只到#20，不能因为命中了#10就发整段；所有依赖须在合法范围内，否则省略该段/回退兼容历史版本。成员数、位置、状态、最新进展也同样过滤。来源不够或索引落后只影响事件补充，普通摘要/原文召回继续。

## 5. 本地自定义表：建议最小结构

这是前端持久化功能，不是只存在Vue内存；无需先部署服务器。

| 逻辑记录 | 建议内容 |
| --- | --- |
| 表定义 | 稳定table_id、显示名称、schema版本、字段定义、适用scope、填表说明、发送/注入策略 |
| 字段定义 | 稳定field_id、显示名、类型、含义、更新模式（覆盖/追加/仅填一次/人工） |
| 行/修订 | 稳定row_id、table_id、版本、字段值、来源引用、人工锁定、作用域 |
| 处理回执 | 按任务/表独立记录来源版本和完成状态，不借用事件或摘要游标冒称自定义表已填完 |

使用固定的`table_definitions`、`table_rows`等通用object store，用户建表是在写表定义记录，不是每加一张表都修改IndexedDB物理schema。字段名可以更改，但稳定field_id不变；类型变更/删列需要明确迁移/保留策略。

建议最小UI：建表、增改字段和说明、手动行编辑、选择是否允许AI填写、选择发送/注入方式、导出恢复。自动填表的全部调度选项不因此默认塞进首版；事件专用任务仅能改事件，不因共享表格UI获得任意表写权限。模型输出受限数据操作，不执行任意SQL/JavaScript。

事件页可复用通用表格显示/编辑能力，但核心event_id、来源/关联、只追加和范围校验是受保护模块，不能被普通自定义表的覆盖操作绕过。现有物品/地点等不因此重建迁移一遍。

本地迁移包须包含用户选择的表定义、行值、schema/策略及必要引用材料。未包含的模块要显式列明；不导出密钥。仅本地不等于永不发送模型，允许AI填写/正文注入时仍按用户配置发送。

## 8. 2026-09-23 手机反馈后的用户明确修订

以下用户新要求覆盖第5节和 W-01 初版 R8 的手动选摘要填表入口，实施仍在 W-01 同分支内，不另开正式任务卡。

- 自定义表改为原生最新楼摘要同一次 LLM 调用的附加 JSON 表格增量；发送各表当前可见内容、字段定义/说明/填写提示词，不另起填表请求。
- 中文写入策略：覆写、追加、首次写入后锁定；旧 manual 保持人工独占，不静默解释为仅填一次。
- 表列表作为主界面；右键/长按菜单管理；独立设计页与单字段五项弹窗；行列表只预览前两列，完整行弹窗编辑；长按多选，隐藏行不发给摘要 AI 或正文模型。可见有效行并入原当前状态注入，遵守仅摘要模式。
- 档案页默认仅状态与说明，不读全量正文/摘要列表；待审核操作按需加载。自定义表页不读取摘要。原摘要页继续保留。
- 表记录协议 tableSchema=2；逻辑导出包 v2，读取 v1 向后兼容；物理 IndexedDB 维持 v1，不破坏性升级。纯历史补摘/高层压缩不读取当前表冒充历史状态；包含最新楼的批量请求返回整批表格净变化。
