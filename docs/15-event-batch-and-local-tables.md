# 全量事件目录、延时批处理与本机自定义表

更新：2026-09-23。状态：第1节为用户明确需求；其余标为建议的计数、字段、调度和短概览方案尚未冻结。本文不是施工卡，未修改柏宝书实现、运行测试、调用付费模型或操作用户设备。

当前入口：`../stages/S-daily-baibai-mvp.md`。基础选型见13，事件规则与召回见14。本轮将14初稿的候选事件检索和概述覆写建议替换为全量目录与增量概述；不撤销既有身份、版本、分支和来源规则。

## 1. 本轮确认需求

- 接受三条事件召回规则：每链最多额外补一条进展，命中/近期正文已包含时不重复补；同链多个命中只包装一次概述及额外进展；标题、概述、最新进展、成员序号和总数均受同一分支/截止点约束。
- 不在事件归组前检索6～10张候选卡。将本次故事/分支/历史范围内的全部可发送事件目录提供给负责事件的AI，包含事件ID、标题、概述、状态、关键词等；已结束或沉寂链也在范围内。全量目录不等于重复发送所有成员正文。
- 事件概述采用增量追加，AI只能补本次新进展，不能覆写、删除或改写此前概述。一次批处理中，同一事件相关的五条摘要仍关联五个实际ID，但只需为这些新增进展追加一到两句。
- 增加独立事件LLM调用途径，可每隔30/50楼或用户指定间隔补齐事件。该调用只处理事件链，使用专用提示词，不重做每回合摘要，不更新物品/人物/变量等动态状态。
- 保留与每回合摘要一起处理事件的途径；两种模式的协作/默认选择由第3节建议细化，不能让同一批材料被两个写入者重复结算。
- 参考 yuzuki-Memory 的处理进度、延后触发和选定范围分批回溯体验。
- 自定义表是项目需求，可本机保存，不以实现服务器同步为前提。用户希望自己决定表、列和记录内容，而不是只能使用固定模板。自定义表是否完整进入同一初版任务、具体编辑/填表能力仍需在正式任务范围中明示，不能把愿景当成已授权全面实现。

## 2. yuzuki-Memory 源码核对事实

固定版本：`gaigai315/yuzuki-Memory@14ddb8df3207f5f8e0ac8af4c93b72edce00f704`，由main引用确认。本次是静态阅读，不是TT/手机运行验证；不拿其代码存在当成任意编辑/分支/持久化场景均已通过。

### 2.1 处理进度与自动触发

`config/task-runner.js` 的 `normalizePointers` 将进度保存在 `state.settings.manualPointers`，分别有 `trace`（填表）、`summary`、`historySummary` 和相应的延期指针。UI另有读取、人工调整和重置这些指针的入口。因此“已处理到哪里”主要由程序记录，不让LLM数表格或猜已经读了多少楼。

`buildAutoTraceTask` 读取填表指针P、当前聊天长度L、自动批次N以及延后量D，达到 `L-P >= N+D`（并满足模式、启用及延期条件）才生成任务；处理的是 `[P,min(P+N,L))`，不是将延后的D楼一并冒充已处理。代码默认批次40、延后2；这是该版本默认，不是Mnemosyne冻结参数。

`runAutoTraceTask` 的成功提交路径设置 `pointers.trace` 为已提交范围末端，并保存结果和指针；保存失败会恢复原内存状态并报告失败。它是该插件的保存流程，不等于已验证跨宿主文件和IndexedDB的分布式事务。

`chatMessagesFromRange` 按当前聊天数组的 `[start,end)` 切片，逐条保留原楼层标识，再过滤插件消息、系统内容及按配置隐藏的消息/标签。不能把其物理范围长度直接等同于实际发送给模型的消息数或摘要数。

### 2.2 手动回溯与分批

`ui/memory-window.js` 的 `buildTaskBatches` 按选定start/end和batchSize拆分范围；任务循环逐批调用，显示批次进度，可停止，失败时可重试或由用户选择继续后续批次。成功批次之后更新界面/任务状态。

所以可以借鉴“显示处理位置→选择未处理范围→按批执行→中断后续跑”的交互，但不直接用单一最高楼层指针证明范围内部没有遗漏，特别是人工跳过失败批次之后。

### 2.3 消息账本与自定义表

`config/floor-ledger.js` 另设 `yzm_memory_floor_delta` 消息标记以及带 `swipe/signature/rows/floorScope` 的账本记录，用于消息删除或swipe变化后的重放。它与上面的自动任务进度不是同一东西；不能只复制计数器而丢掉来源校验。

`ui/memory-window.js` 有自定义表定义的规范化、全局读取/保存入口，使用 `yzm_memory_global_custom_tables`，优先通过GlobalSettings访问，缺少时回退localStorage；表定义包含ID、名称、列等，运行状态使用tables/records。此处是应用层表定义，不是每建一张用户表就执行一次SQL建表。没有将其整个宿主存储架构认定为纯本机或等同Mnemosyne后端。

复用结论：借鉴交互和状态机；不整包搬运该插件、不替换柏宝书的摘要/原文升级召回。源码复制前单独核对许可；本轮没有复制其实现。

## 3. 事件调度建议

### 两种模式，共用一套已处理记录

| 模式 | 输入和职责 |
| --- | --- |
| 随摘要处理 | 既有摘要/状态请求附上全量事件目录，事件操作作为独立输出类别；未返回事件字段不能假装该回合已检查 |
| 独立批处理 | 专用事件提示词 + 当前批次实际正文/已有L0摘要及ID映射 + 全量事件目录；只建/续事件、增加关联、追加概述和更新本事件元信息 |

建议同一故事/分支只选择一种自动事件处理模式。两种入口共用处理记录、幂等键和串行提交；手动补齐只补未处理/失效范围。切换模式不清空已成功材料，也不重跑状态delta。

建议日常默认独立批处理，保留随摘要处理可选。此默认是建议，不冒充用户已选择。间隔N、每批最大输入、延后D区分配置；输入超预算可拆小批，但不能截断原文后标记整批已处理。用户选择30/50不代表30/50条摘要。

计数口径需在UI显示：宿主楼层/消息范围与实际L0/回合数分开。建议触发用明确的消息楼层范围，执行边界不截断普通User+Assistant配对；最终范围由保存的SourceRef及摘要版本集合确定，不能以移动的显示楼层号作永久身份。最终默认单位和D数值尚待任务定档。

每批开始固定输入范围、正文/摘要版本、事件视图及提示词版本。依次处理批次，后批读取前批已提交的新事件表；不让整轮回填始终使用启动时同一份旧表。回溯历史时使用该历史边界下有效目录，不将未来标题/概述带进过去。生成结果落地前复核源版本和事件视图，失配不得直接覆盖。

前台剧情生成、摘要与事件模型任务的调度应有明确优先级，不能无限抢占或创建重入请求。手机WebView被挂起/关闭时不承诺继续调用；重开由持久进度发现待处理范围。本文描述产品调度，不是安排ChatGPT后台定时任务。

### 输入材料和摘要ID

独立事件任务只发事件相关指令和必要剧情证据，不附带整套动态状态填表提示词或无关记忆表。本批正文可以连贯提供，摘要ID映射由程序附加，不让AI为尚未生成的摘要编ID。

建议首版在L0可用后挂接；没有摘要的楼显示为待摘要依赖，不强制重做摘要，也不伪造关联。可接受的历史无正文摘要继续带来源声明。批次中每个已检查的摘要都要返回可验证的处理结果，缺ID/缺输出是未完成，不解释为无事件。

## 4. 已处理与缺口：我们的建议

进度按 `story_id/branch_id/task_kind` 区分；自定义表未来需要独立table_id进度，不能拿“事件已处理”证明新建表也已回填。建议持久记录：任务/批次ID、输入快照和有序SourceRef/摘要版本、输入指纹、提示词或处理规则版本、输出ID、处理结果、提交状态。

显示至少区分：总范围、已检查、待处理、需复核；另显示事件已关联摘要数。已检查且明确无事件也计入已检查，不能因没有输出事件就无限重试。

正常追加可用连续已完成前缀指针加速，但每批范围/版本是事实依据。人工跳过、模型遗漏、失败、缺摘要和修改旧楼形成显式缺口；最高已处理位置之后的计数不能掩盖内部缺口。允许继续后批时也不把缺口写成完成。

事件追加条目、成员关系、事件当前视图和该批处理回执在同一IndexedDB事务中提交。模型请求在事务外。相同batch_id与相同输入重复提交不再添加一次相同概述；同ID不同输入拒绝。模型失败、解析不完整、来源失配或保存失败均不推进完成状态。

正文编辑、swipe或摘要重摘后按实际版本检查受影响事件材料；依照12的人工兼容审核，不自动全库重摘。用户修改关联后标记相关派生概览待更新，保留原概述条目及更正记录。恢复/迁移必须带进度回执，否则换机不能知道哪些范围尚未处理。

## 5. 追加概述与召回短版的未决取舍

用户已确认的是：**事件历史概述只追加，AI不改以前内容。** 建议保存一组独立的进展条目，每条包含其一到两句增量概述和本批相关摘要版本集合；不是反复重写一个越长越大的长字符串。

它会随事件发展变长，不能同时无条件满足“无限追加”与“整个事件总览永远只有一到两句”。这属于输出预算选择，不是IndexedDB性能问题，也不是改变全量目录要求的理由。

建议另存版本化 `recall_brief`：只用于事件卡折叠导航/正文召回的一到两句短概览，可由同一次事件处理调用额外产生并缓存；不覆盖或替代增量概述记录，不在每次召回时再调用一次LLM。来源和截止点与事件资料一致，过期/未生成时不当成完整总览。

**recall_brief尚未确认，不可在施工中悄悄把它当成用户允许覆写历史概述。** 替代方案是召回只取有限条有来源的概述片段，明确标为“事件片段/起因与最近进展”而非全链总览。两种方案都必须遵守已确认的同链去重、额外进展上限和历史范围。

全量目录也受模型上下文容量约束。发送前估算目录+正文+输出预算；不足时先缩小本批正文。仅目录就放不下时暂停事件任务并提示更大上下文/用户选择的分批目录方案，不静默退回Top-K、删除旧概述或发送截断表。随摘要模式可保持原摘要/状态工作，事件明确排队待处理；不能假称已经完成事件更新。

## 6. 本机自定义表建议

用户体验是自定义数据库表，物理实现建议使用固定的通用记录集：表定义、行数据、变更/版本和填表进度。用户新增表或字段只是写元数据，不要求每次变更IndexedDB的object store；数据库自身真正的索引/结构升级仍需版本化。

建议定义保存稳定table_id、schema_version、名称、字段ID/类型/说明、AI填表规则、手动锁定规则和注入策略；行保存稳定row_id、table_id、story_id/branch_id、values及来源/版本。字段改名不改字段ID，删列/改类型不静默丢弃旧值。默认不把名称当身份。

建议最小能力是建表/改列、手动行编辑、可选AI填表、选择随摘要或独立批处理、注入开关及独立role/位置/长度。每张表拥有自己的填表范围和进度；新建表是否追溯旧聊天由用户明确选择，不能因为其他表已处理到500楼就认为新表也已完成。

所有内容先存在本机IndexedDB，并纳入可迁移包；不要求VPS、远程数据库schema或跨设备自动同步。‘不上传数据库后端’和‘不发送给LLM’是两种权限：禁发/未勾选给该任务的表不出本机，AI填表必然要发送授权的相应内容。

自定义表的UI和调度可与事件表共用基础组件，但正式事件ID、来源关联、追加概述与进度是受保护的内置结构，不能让用户随便改列就破坏事件召回。自定义表不自动获得事件链能力，也不自动进入向量库；是否索引是后续独立策略。

本文记录自定义表需求和实现建议，不将通用表编辑器、复杂类型迁移或所有表自动填充悄悄并入已确认的事件MVP工作量。正式任务卡须单列其交付范围和估算。
