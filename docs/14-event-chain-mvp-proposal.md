# 初版事件表与有界事件链召回

日期：2026-09-23。状态：事件表、人工关联、事件链召回进入初版是用户明确需求；本文件的字段、自动判链规则、默认额度和版本实现为 proposed，未施工、未验收。不是任务卡。

前置选型见 13；阶段入口见 `../stages/S-daily-baibai-mvp.md`。沿用柏宝书分支前端及摘要/动态状态模型，先扩展现有流程，不另建第二套前端、摘要助手或图数据库。

## 1. 产品目标与术语

事件链是围绕一个明确事项、目标、冲突、约定或重要变化组织的已发生剧情证据集合。它不是人物一生、全部同地点剧情或一切主题相似文本。一次独立、有后续价值的事件也可以先形成单条链；不要求等第二次出现才允许创建。

例如“借出玉佩—约定归还—归还时发现裂痕”可以属于一条链；同一个人在客栈吃饭不因此加入该链。跨楼、跨场景、相隔很久仍可延续；同楼可以涉及不同事件。生活日常不因题材日常而排除，有明确承诺、冲突、关系变化等仍可成链。

首版实现事件归组及有序证据，不声称已经实现任意事件之间的因果图。链内先后不自动等于因果关系，模型不得从相邻、同名人物或同一物品推断不存在的原因。

## 2. 摘要 AI 怎样知道可加入哪些链

不是依赖模型记住数据库，也不是每次把全部旧摘要放进请求。在现有摘要请求前构建有界候选事件卡。

候选来自：当前正文匹配的事件标题/别名/关键词/概述，最近有关联的活跃链，用户固定的链。复用现有词法/向量能力；检索范围包含沉寂或已结束的旧链，不能只提供最近活跃事件。进行中或固定只影响优先级，不绕过故事/分支/截止/隐私过滤。

建议首次试用目标为约 6～10 张候选卡，并有总长度限制；数值是待试用参数，不是冻结字段或正确性保证。固定/近期列表不能占满预算、挤掉相关旧链。

每张卡提供稳定事件 ID、标题、状态、截至被摘要回合之前的概述、少量关键锚点、最新有效进展及来源标记。模型同时读取本回合 User+Assistant 原文及现有摘要上下文。无需给出全部成员 ID，更不能仅凭模型内部知识编造旧 ID。

事件目录少时可在预算内给全目录；目录大后检索只减少候选，并不能保证不漏链。候选没出现不等于数据库没有该事件。模型发现“明显续接旧事但卡片不足”时返回待确认，不能被迫另建一个同名链。首版不加入无限递归查询、全库 LLM 扫描或每轮额外判链 LLM。

模型可在原摘要/状态输出中附加事件操作：新建、追加进展、仅提及、无事件、待确认。事件 ID 由程序生成；追加只能选择本次提供的合法候选 ID。程序把新摘要版本绑定到本回合，模型不用预测尚未落库的摘要 UUID。批量摘要需要逐回合或有界块内顺序应用，后一个回合能看到前一个刚创建的链，不使用整批同一份过时目录。

## 3. 判链提示词的建议核心规则

以下是拟新增的事件专属规则，不覆盖物品/人物/生活档案的既有筛选规则。

> 事件链记录已发生、值得跨回合追踪的一个具体事项及其进展。对本回合先判断是否有实质进展，再选择给定事件卡中的同一事项；同人物、同地点、同物品、时间相邻本身不足以证明同一事件。已有事项出现后续行动、结果、转折或新证据时加入旧链；明确独立的新事项才新建。不重要的零散动作可不归组。单纯回忆或重复提及可标为提及，但不伪装成新发生的进展，不改变当前结果。证据不足时待确认，不编造关联、动机、结果或未来发展。只改本轮确实推进的链。

新建或进展更新同时输出一到两句新版概述，以及本轮对该链的简短贡献和可定位依据。概述保留“因何开始/核心事项—重要变化—当前结果或仍未解决之处”；不要只把概述改成最新一楼的复述。未结束和未知应明确，不擅自推演结局。

只提供旧概述并反复压缩有丢失关键起因的风险。建议候选卡额外保留少量起因/关键转折锚点（短句及稳定来源引用），更新读取这些锚点、旧概述与本轮正文。锚点是可验证证据提示，不复制全链，也不保证两句话能无损概括长故事。

模型输出通过格式、合法 ID、来源版本和范围检查后可自动采用；这些检查不能证明语义关联一定正确，用户仍可改链。模型不自动合并/拆散旧链，不移除人工锁定关联；不靠一个自报置信度分数冒充验证。

### 与现有提示词的兼容

固定核对版本 `393873acd27906a09308ae65fe7e636a3d3941ab` 的 `prompts.ts` 已有 history/state 宏及结构化增量输出；`RULE_LONGTERM_DB` 同时禁止把一次性事件等写入 summary 以外的字段。因此新增事件模块必须明确“事件索引”是独立规则类别，不能原样继承该禁令。自定义提示词、单楼摘要和批量摘要都要覆盖这一规则，不能只修改默认提示词。

若用户自定义模板没有返回事件操作，现有摘要/状态仍可保存，事件标记未处理；不能把缺失字段误解释成无事件已确认。独立补建事件可作为显式修复入口，不默认再重复结算物品/状态。

## 4. 最小逻辑数据结构（待冻结）

正文、摘要及宿主映射沿用 13 和既有领域语义。事件模块建议分成三组逻辑记录；这不是现有 schema_version=1 已支持的新字段声明。

| 记录 | 建议内容 |
| --- | --- |
| EventChain / 分支当前视图 | 稳定 event_id、story_id；按 branch_id 保存 current_event_revision_id。标题不是主键，同名不能自动合并 |
| EventMembership / 关联变更 | 稳定 link_id、event_id、摘要 memory_id 与实际 memory_revision_id、关联类型 progress/reference、可选本事件贡献短句、创建来源 AI/manual、人工锁定；新增/移除操作绑定事件修订 |
| EventRevision | event_revision_id、event_id、branch_id、basis_snapshot_id、previous_revision_id、title、overview、status、keywords、少量 anchors、实际 input_refs、成员变更、操作幂等标识、时间；保留生成/人工编辑来源 |

成员关联是多对多，不把一个摘要永久限制在一条链。底层引用摘要版本，不把楼层号或 AI 生成的链内序号当身份。UI 显示当前宿主楼层、摘要短 ID 和链内位置；程序按当前有效来源顺序计算，剧情时间是辅助维度。

链内成员不每次复制全部摘要内容，事件修订不每次嵌入一份无限增长的成员数组。当前成员/逆向索引可作为物化视图，在同一版本化关联日志上重建；历史修订通过不可变增删材料还原，不只剩一张被覆盖的当前表。需要链到成员、成员到链两个方向的索引以及分支/来源顺序分页。

UI 看起来是覆盖概述，存储必须追加新修订并切换当前指针。旧概述及其依据保留，不原地改旧 input_refs。现有 06 的 checkpoint 自依赖只对 Record 开放；不能把 Event 的累计更新直接套用成已验证的 Record 规则。本模块应独立版本化定义其来源/累计检查点及有效性，再接核心校验和导出，不声称已有契约自动支持。

## 5. 更新、人工编辑和历史范围

正常新增进展时，候选卡来自本回合以前的有效视图；新概述以本回合已归档原文为界。新摘要/事件修订/成员变更在程序确认同一源版本后发布。模型请求在写事务外执行；提交时复核摘要/事件视图版本，手动修改或新回合已推进时不让迟到结果覆盖。

旧回合补摘、swipe、恢复旧快照和分支使用各自历史边界。概述、锚点、最新进展、成员总数、链内位置都来自同一有效范围。只过滤成员却仍使用未来更新后的概述仍是串剧情。

正文/摘要编辑按 12 的人工审核策略处理；链的概述也检查实际依赖。正文保留兼容确认不伪造摘要来源；摘要重摘、移出成员或改链可能使概述待重建。不可把待重建概述继续发送；可降级为仅命中摘要与有证据的关联标记。

用户可以手动加入/移除历史摘要、改事件名、修订概述或标记状态；手动关系不被 AI 静默撤销。手动加入记录不等于概述已更新，界面应提示“概述待更新”并提供明确重建动作。合并/拆链可后续增强，初版用移出/加入已有链满足基本整理，不让 AI 自动进行全链大改。

## 6. 事件表前端

在柏宝书现有界面加一个事件页，不先重写原页面。事件卡默认折叠，显示标题、状态、一到两句概述、成员数和最后进展来源；可搜索、筛选。

展开后分页展示关联摘要，默认每条前 50～100 字，点击展开摘要/正文。提供来源楼层/短 ID，用户可通过选择摘要或粘贴可解析 ID 加关联；不存在、版本不适用或越界的 ID 必须解释失败，不猜同号楼层。默认按来源顺序，剧情日期另列；倒叙不破坏来源顺序。

编辑窗口应能确认当前故事/分支，过期或待确认关联有标记。长链只分页加载，折叠卡的概述是导航，不是隐式删除早期证据。

## 7. 有界召回与注入

沿用既有 Query、向量/BM25、RRF、rerank、原文升级与补位额度，事件包装放在候选选中之后：先完成原检索，再从实际命中的摘要找所属链，读取本次范围可用的事件修订和最新进展。

默认结构：命中摘要或已升级原文 + 一份链名/位置/概述 + 至多一条额外的最新有效进展摘要。最新进展优先取 progress 类型，不把后来单纯提及的楼当成事件继续发生。尾条涉及其他事件时，可使用落库时生成且有来源的本事件贡献短句，仍提供完整摘要查看。

示例（合成）：

> 【相关回忆｜来源 #120】
> 命中内容：甲将玉佩交给乙，并约定节后取回。
> 所属事件：玉佩借还｜本次范围内第 3/10 条关联记录
> 事件概览：甲为帮助乙暂借玉佩，取回时发现裂痕，双方仍在查明损坏原因。
> 最新有效进展（#380）：乙承认曾把玉佩交给第三人。

这表示事件索引截至本次范围的记录数，不宣称数据库已完整收集现实/故事中该事件的所有过程。

### 控量与去重

- 同链多个命中只附一份概述和至多一份额外进展；原检索已选的有效命中不因归链机械删掉。只有单条主命中时，刚好是用户提出的“两条摘要 + 一段概述”。限制的是链扩展，不默认限制整轮全部记忆只能两条。
- 进展就是命中本身、已在其他召回块或近期全文窗口出现时不再重复。已有全文能表达的摘要也不再补发。
- 同一摘要属于多条链时，首版默认只附与本次查询最相关的一条，人工指定可覆盖；其他关系保留在 UI，不展开全部。
- 事件扩展有独立的链数量、长度/token 预算，并计入总上下文。建议起步每轮最多补 2 条链，每链最多额外 1 条摘要；数字待用户试用。超预算先保命中证据，再保概述，最后才补进展，不用事件包挤掉全部原检索名额。
- 两句话及两条摘要不能保证提供完整因果证据。用户追问中间关键过程时仍由原检索命中相关记录，或在 UI 展开；首版不因为链长就自动注入全部十条，也不做递归图遍历。

本轮发送前再次检查 run、story/branch、截止、正文/记忆/事件视图版本及隐私；事件修改要使相关缓存失效。无合法概述/进展时只给命中本体，提示索引待更新，不为凑两条发送失效或越界内容。无事件归组不阻断现有普通召回。

## 8. 初版边界与有限验证

范围：在柏宝书当前分支实现可迁移正文/摘要库、事件索引/编辑页、同摘要请求判链与概述更新、上述有界召回包装。不加 VPS、独立实体库、多主同步或任意因果图；不重做现有检索算法。

旧摘要先保持普通可召回，不默认全库付费回填事件。建议从新回合开始写事件；旧资料可人工挂链或选择范围顺序补建，仅补事件，不再次施加旧 delta。

完成线建议覆盖：新链/续接沉寂旧链/不相关同名/单纯提及；同楼多事件；同链多命中/最新已在全文窗口的去重；长链固定扩展预算；编辑/分叉/回溯不读取未来概述；人工锁定和迟到 AI 结果；新设备导入后 ID、关联、概述版本和索引可恢复。

事实边界：本次只审阅源码与文档，未运行程序或实机测试。用户确认当前 TT 手机 + 柏宝书日常流畅，不把旧 Mnemosyne Demo 的读写放大归因于该模式，也不把当前用户体验冒充新增模块已验证。
