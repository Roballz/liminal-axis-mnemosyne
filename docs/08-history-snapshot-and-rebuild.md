## 1. 用户确认的产品规则（accepted）

1. B 版接受一个记忆库同一时刻仅有一个权威写入端；用户长期 RP 主要在单台手机进行，暂不做离线多端并发合并。
2. **已经发生的剧情以该分支有效历史正文为权威。** 人物状态、关系、物品交接、势力变化等是正文派生结果，不是另一套可以独立改写历史的权威数据。用户大纲/指令不自动变成已发生的事实；角色卡/世界书属于初始设定，不因为修改当前配置就静默重写既有历史。
3. 导入/修改历史时，可确认匹配且仍适用的回合记忆复用；不匹配或已失效、又无适用已存版本的回合重新生成。包含这些回合的大小总结、事件串及相关累计状态也必须退出当前有效记忆并重建。
4. 不为“玩家单改历史人物状态、不改正文”的假定玩法建设通用依赖框架。来源追溯与摘要层级的重建关系仍是实现上一条所需的最小关系，不需要用户手动维护。
5. 继续接受不可变正文版本、分支固定历史、证据不足人工映射、普通 User + Assistant 一轮一份记忆、B/A 共用核心与停写迁移的方向。Head 方案已在本轮确认；非标准回合例外、存储 provider 和恢复实现仍需定稿/验证。

## 2. 两类问题不能混为一谈

### 2.1 身份未决不是“让 LLM 重新生成就能修复”

导入时先确定哪个宿主档案对应哪个故事/分支、哪些消息相同或修改。仍有歧义的区域进入 needs-resolution，不调用 LLM 猜消息身份，也不生成正文填补缺失。确认新历史后，再复用或重建派生记忆。

原文存在而摘要缺失：可以重摘。原文缺失：只能保留明确的 derived-only 状态或由用户补充，不能伪造历史。新旧正文自身冲突：由用户修改/分叉，摘要器不擅自改写后续原文。

### 2.2 权威性与加工来源不同

人物状态不是独立历史真相源，但一份大总结仍要知道自己用了哪些小总结。V1 不建立另一套“状态事实互相支配”的知识依赖系统；只维护正文驱动的加工关系。

建议把两种引用统一为同一种轻量输入关系：原文版本引用，或下级派生版本引用。每条输入都是不可变版本；高层结果的根最终回到正文，或明确标记的初始设定/无原文导入来源。

最小记录建议：

| 信息 | 作用 |
| --- | --- |
| `input_refs` | 本对象实际读取的正文版本/下级派生版本，自动记录；有序输入不排序丢失顺序 |
| `coverage` | 本对象负责覆盖的来源区间或明确集合，以及该次成员与顺序指纹 |
| `recipe_id` / `input_fingerprint` | 保存抽取规则、已知模型/profile 与输入指纹，便于复用、主动重摘和诊断，不构成独立剧情真相源 |

不记录每个角色字段间的推理依赖，不长期复制整套提示词为默认前提。不把“模型后台或模板换了”自动解释为历史正文改变；既存记忆是否升级由明确重摘/兼容规则决定，迁移 B→A 不因 provider 改变而全量重摘。

### 2.3 不重复造框架，但也不能遗漏实际输入

普通回合摘要以实际 User + Assistant 正文为主要输入。若确实还把先前正文/小结发给提取 LLM，用于理解“他”“仍然”等语境，则这些也放入同一份 `input_refs` / 覆盖范围，不能因为最终摘要只引用本轮就隐去它们。无需另建通用生成依赖系统或让用户填写。

未传给模型且不参与规则求值的数据，不凭想象加依赖。非正文独立模块只在实际被使用且需要可追溯时记录其输入版本；具体模块需求未出现前不扩建。

## 3. 重建与复用规则

### 3.1 从受影响回合向上重建

例：回合 R12 变化；小结 S2 覆盖 R10～R15；大总结 L1 包含 S2；事件 E 使用 R12 和 R18。

R12 的旧回合记忆、S2、L1、E 先在目标分支标为不适用/待重建；不受影响的回合 R10、R11、R13～R18 仍可复用其局部记忆（前提是它们实际输入未受影响）。不得借用旧 S2/L1/E 暂时注入。

按正文 → 回合记忆 → 小结/事件 → 更高层结果的输入先后顺序重建；有相同有效输入与适用版本的已存结果时可复用，否则重新生成。共享旧对象不就地覆盖，不在所有分支全局删除。

对累计人物/势力状态，应从变化点之前最近的有效状态检查点开始重放受影响后缀；后面正文没改，不保证累计状态不变。但不因此重新生成无关回合的局部摘要。

### 3.2 插入、删除、重排也会改变覆盖范围

只检查旧 input_refs 是否存在不够：在 R10 与 R11 之间插入新回合后，旧范围总结可能没有任何旧引用失效，却已经遗漏新剧情。

区间总结需检测其范围内成员与顺序是否变化；显式非连续事件集合也要保留成员版本，修改区间触发相关事件关联的局部复核。无需推断全世界所有潜在因果，也不能把旧事件的成员列表当作永远完整。

楼层平移本身不等于正文版本变化；以已确定的消息身份和逻辑区间判断，而不是因显示编号变化重摘整个后缀。

### 3.3 暂停、恢复与分支隔离

“失效/待重建”属于目标分支及其历史/记忆视图。相同 R1 仍被子线采用时，R1 记忆可以在子线有效，父线改到 R2 不应使子线跟着失效。

受影响的记忆服务在重建/复核完成前不声称完整，不把过期结果发送给正文模型。修复写入和有效原文归档仍须允许，否则无法解除暂停；无关故事不受牵连。具体按分支还是更细作用域暂停由后续上下文契约定稿。

生成异步结果提交前重新核对该对象的实际输入与覆盖范围。仅仅追加了范围外的新剧情，不使旧回合摘要任务无条件过期。用户切回旧 swipe 时可复用其先前适用结果，不必重新调用模型。

## 4. Head 与历史清单：已确认结构

### 4.1 三个层次，各管一件事

| 层次 | 字段/形式 | 语义 |
| --- | --- | --- |
| Branch 的 Head | `head_snapshot_id` | 可更新的指针，指向该分支当前已完整提交的历史快照 |
| 历史快照 `HistorySnapshot` | `snapshot_id = hs_<UUIDv4>` | 不可变的历史版本记录；不编码楼层、剧情时间、宿主或数据库 |
| 历史清单 `HistoryManifest` | 不可变的有序 `(message_id, revision_id)` 清单，根引用 `manifest_root_id` | 表达该历史采用哪些消息、各用哪版正文以及先后顺序；不嵌入全部正文/摘要 |

内部 ID 采用带类型前缀的 UUIDv4，小写标准连字符格式，安全随机生成，写入检查 ID 唯一性；冲突不可覆盖，不能用 Math.random/剧情时间生成。RFC 9562 §5.4 描述 UUIDv4 的随机生成方式。它不是来自 TT integrity，也不依赖服务器在线。下面 H1/H2、M1/R1 都只是人工示例缩写。

### 4.2 历史快照最小字段

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 快照格式版本，初版 1；不是剧情版本计数 |
| `snapshot_id` | 本次不可变快照 ID，`hs_<UUIDv4>` |
| `story_id` / `branch_id` | 所属故事、提交所归属分支 |
| `previous_snapshot_id` | 同一分支上一份已提交快照；分支初始快照为 null |
| `manifest_root_id` | Mnemosyne 自己的不可变清单根 ID，不是 TriviumDB NodeId/数据库行号 |
| `message_count` | 该清单消息条数，可由清单校验；不是版本身份 |
| `change_kind` | init/import/append/edit/swipe/regenerate/delete/reorder/restore/fork 等有限原因；须与实际变更相符 |
| `operation_id` | 本次业务操作的去重键，同一操作重试不创建第二个快照 |
| `created_at` | 实际记录时间，用于审计，不承担剧情顺序/有效性判断 |

Head 只保存指向快照的引用，不再同时制造一个内容相同但含义不清的“head_revision”编号。旧 examples 中 head_revision 字段在正式 T-02 中统一映射/更名，并记录旧样例变更，不能默默修改已实现接口。可读的“主线/第8421楼/剧情日期”仅为界面标签，不作为 ID。

`message_id` 与 `revision_id` 已在正文档案中关联。一个快照内，同一 message_id 原则上只出现一次；需要两条重复文本时是两个消息身份，不因文本相同合并。role、正文和影响正文含义的来源信息位于对应原文版本；filename、屏幕 index 等易变宿主信息在映射层维护。

### 4.3 清单存储：分块共享，不每轮复制整份历史

从 B 版起采用不可变有序分块目录，块及目录节点使用 Mnemosyne 内部 ID。叶块保存有限数量的消息/版本引用，目录保存有序子节点与条数。修改只新建受影响的块及通往根的目录路径；旧快照继续引用旧块，其他块共享。插入/删除通过局部拆分/合并维护，不把绝对楼层号写进每个后续项而全量平移。

块尺寸、扇出、缓存及底层索引布局是 T-03 的实现/性能参数，不要求用户选择；块编码在 T-02 先定义最小可校验格式，T-03 再落实持久化算法。逻辑导出必须完整保留快照 ID、顺序和版本引用，并包含解析根引用所需的对象。未来可以有无损重打包的迁移程序，但不能直接把不同根内容写回同一已发布快照。

内容校验/导出包/派生输入使用 SHA-256 与版本化 JCS 编码的技术基线，输入字段表由 T-02 固化；**Head 本身不需要对整部小说重新计算 hash**。UUID 身份与内容指纹分离，不承诺同样内容、不同分块布局有相同根指纹。RFC 8785 规范 JSON 序列化但要求保留字符串数据，不对正文私自去空格或做 Unicode 改写。

## 5. 如何生成新版本

一次明确的历史业务变更对应一次提交，而不是每次 token、事件回调、刷新窗口都建快照。

1. 解析实际宿主操作并确认当前绑定/原文状态；识别不清先 needs-resolution。新正文版本先归档，未选中的候选可保存但不必推进当前历史。
2. 基于当前 Head 计算新的有序消息/版本选择，复用未变正文和清单块。
3. 生成并持久化一次操作的 snapshot_id/operation_id；重试沿用本次操作身份，而不是重新生成另一套 ID。
4. 持久化全部新正文、清单对象、快照与必要重建/失效记录后，才发布新的 Head；处理过程中已发现变化就先阻止旧 prepare 结果应用。
5. Head 更新要求仍基于预期旧 Head。A provider 可用真实事务/条件写入；B 必须通过单权威写入协调和经过崩溃测试的发布协议提供等价边界，不能假定 TT 提供未验证的跨调用事务。
6. 发布后复用仍适用的记忆并重建受影响派生对象。若原文已提交而派生未完成，分别显示“原文已同步”和“记忆重建中”，不把旧结果冒充新结果。

| 操作 | Head 是否变化 |
| --- | --- |
| 新增稳定消息（包括新 User 输入） | 是；一轮摘要仍等配对可用后生成 |
| 编辑旧消息、切 active swipe、成功 regenerate 改变 active 正文 | 是，即使楼层数和最后一句没变 |
| 删除、插入、重排当前历史 | 是 |
| 重复导入且确认当前有效历史完全相同 | 否；重复操作返回原结果 |
| 打开/改名聊天；显式换新聊天文件承载但逻辑历史不变 | 否；更新绑定版本并使旧运行上下文失效 |
| 重做摘要/大小总结/embedding、修改检索策略 | 否；更新相应派生/记忆视图或策略版本 |
| 故事时间倒退的正常回忆/倒叙 | 由实际新增/修改消息决定，不从剧情时间推导 |
| 回滚到曾经采用的旧历史 | 建新快照，可复用旧清单根，不把 Head 直接拨回旧 ID |

回滚建立新快照用于区分“同样历史再次被采用”和“从未发生变化”，避免旧运行结果因 ID 恢复而被误接纳。新增快照不重复复制正文。

失败 regenerate 若宿主最终仍保留原文、不改变选择，不发布假的成功快照；若失败确实留下删除/空槽等不同状态，必须继续校验并记录实际变化或进入修复态，不能自动假装旧正文仍是宿主当前版本。中间删除事件不单独解释为永久领域删除。

## 6. 分叉与异步边界

### 6.1 分叉固定父快照，不读取父 Head 的未来状态

Branch 的不可变 fork 记录包括：parent_branch_id、source_snapshot_id、prefix_length，以及非空前缀最后一项的 `(message_id, revision_id)` 校验锚。prefix_length 是固定父快照中从头继承的项数：包含分叉消息；空前缀为 0/无锚。创建时校验锚与父快照一致。

新分支创建自己的初始 snapshot_id，previous_snapshot_id=null；清单是固定父快照的前缀（可共享块），随后自身追加。父线以后编辑共同旧楼时，子线仍引用原来的正文版本。

例：H1 的清单为 `[M1/R1, M2/R1, M3/R1]`。子线从 M2 分叉，只采用前两项。父线改 M1 后产生 H2，清单为 `[M1/R2, M2/R1, M3/R1]`，子线继续采用 M1/R1。回合记忆或事件若跨过 M2 截止点，不能整条继承。

### 6.2 Head、Run 与记忆进度不混为一项

本轮 prepare 应捕获 branch_id/head_snapshot_id、宿主绑定/观察代次、run_id，以及记忆视图/策略输入。最终发送前复核，存在未同步变化也不能放行旧结果。Head 未改不代表模型输入一定没改，例如单独修正提取错误、策略变化、切聊天都应使相关准备过期。

后台历史摘要提交则核验它实际依赖的版本和覆盖范围，不能因在范围之外继续聊天就无限丢弃重算。上层总结必须等下层新版本就绪；保留旧结果作归档不等于允许注入。

## 7. B → A 与验收例

迁移保留内部 snapshot/message/revision IDs、清单与块、fork 记录、派生输入/覆盖关系、operation 去重结果与未完成重建进度。更换 TriviumDB/服务器数据库不改变历史身份，不强制重摘正确摘要。单写端切换和恢复的原子性/持久性仍由 T-03 实测，不能仅凭“手机长期单端”省略崩溃恢复。

正式 T-02 需要覆盖至少以下正反例：

- 旧楼正文变了、总消息数和尾消息不变：Head 必须变，相关上层记忆失效。
- 父线改共同历史：子线历史/仍有效记忆不变。
- 在总结覆盖范围中间插入新回合：即使旧引用全部还在，总结也需要更新。
- 在范围之外追加剧情：局部旧回合记忆复用，累计总结按自身范围处理。
- 同一逻辑档重复导入：不重复建正文版本/快照，不重复付费重摘。
- 输入身份仍有冲突：不让 LLM 猜 ID 或补造正文。
- 原文不变但纠正摘要提取错误：只更新派生/记忆视图版本，Head 不变，依赖旧摘要的上层结果重建。
- 回滚到旧清单：内容可复用，但新快照 ID 不同；旧 run 不复活。
- 进程在写新块后、发布 Head 前终止：不能露出不完整 Head；恢复规则需实际演练。
- B 导出到空环境/A：快照与有效历史一致，派生正确结果仍能复用。

## 8. 依据与未决边界

用户确认是本文件产品规则来源；既有接入证据在 T-02A 任务和运行记录。本文件是设计，不是外部材料中的现成 Mnemosyne 实现。

技术参考：
- UUIDv4：[RFC 9562 §5.4](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.4)。
- 确定性 JSON 编码及字符串保留：[RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html)。
- 内容、目录与提交分离的类比：[Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)。不使用 Git 管理实际 RP 数据，不照搬 Git 文件格式或 SHA-1。

尚未确定的产品/实现边界：非标准回合自动分组、对象品牌名、完整 ContextBlock 渲染/配置、旧档模糊对齐阈值、保留清理、provider 的实际恢复能力。T-02 只落实已确定规则及安全的未决状态表达；不得把这些项静默定案。具体24项收口和测试边界见正式 T-02 卡，T-03 卡目前是 proposal。
