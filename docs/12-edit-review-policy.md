# 正文编辑审核与摘要失效策略

日期：2026-09-22。状态：accepted（产品/领域策略；尚未实现）。适用未来摘要与编辑工作流，预计在 T-07 及后续前端中落实；不回改已验收 T-04/T-05 的历史证据。

## 1. 目标

用户实际 RP 中会频繁进行小幅正文编辑，例如错别字、措辞、单句逻辑修正。不能把每次编辑都等同于剧情重写并立即级联重算全部摘要；同时也不能静默把旧摘要当作一定仍匹配新正文。

原则：**正文版本立即、无损记录；摘要是否需要重生成由用户人工确认。**

## 2. 编辑发生时

1. TT 编辑仍产生新的 SourceRevision，并推进该 Branch 的正文 Head；旧 Revision 保留审计，不原地覆盖。这是正文事实层，不因“只是错别字”而跳过版本记录。
2. 若编辑命中一个可精确定位覆盖关系的 L0 摘要/TurnMemory，该卡片进入 `needs_review`，前端显示红色标签，例如“正文已编辑 · 待审核”。
3. 不因一次 edit 自动调用 LLM、不自动重生成 L0，也**不立刻把 L1/L2/L3 全部判成需要重建**。上级先表现为“等待下级审核/受该审核阻塞”，因为用户可能确认旧 L0 仍完全适用。
4. 多次编辑落在同一待审核 L0 时合并为一个待审核事项，指向最新正文版本/Head，不重复弹窗。
5. 没有摘要覆盖的正文只记录新 Revision，不制造空审核卡。旧导入摘要若来源/coverage无法精确证明，不按楼层猜受影响关系。

## 3. 摘要卡片操作

待审核 L0 提供至少两个明确操作：

### 保留摘要

用户确认“正文虽改过，但该摘要内容仍成立”。

- 不修改旧摘要的生成来源记录，不把旧 input_refs 偷换成新 Revision。
- 记录一条**用户确认的兼容审核事实**：该摘要版本在指定新正文 Revision/当前 Head 下仍可继续使用。
- 清除该卡片的红色待审核状态。
- 因 L0 内容/选择没有变化，依赖它的 L1/L2/L3 保持有效，不触发级联重建。
- 该兼容确认必须有明确 scope/版本，后续再次编辑不能无限继承旧确认。

这需要未来 validity 层增加“reviewed compatible source change”一类显式审核记录；不能通过篡改 provenance 或假装摘要重新生成来实现。

### 重新生成

用户确认本次正文改动会影响 L0 摘要。

- 原 L0 摘要版本保留历史，新生成一个基于当前正文 Revision/Head 的 L0 版本。
- 新 L0 被选为当前版本后，所有实际依赖旧 L0 的 L1/L2/L3… 标为 `needs_rebuild` / “下级已变化”。
- **不自动级联调用模型。** 用户从 L1 开始按层手动重新总结；每层生成并确认后，下一层再恢复可重建状态。
- 依赖图决定受影响范围，不粗暴使整个 Story 的所有高层总结失效。

## 4. UI 与交互

- 默认不为 edit 弹阻断式窗口；在对应 L0 摘要卡片上显示明显红色 tag，并在摘要工作台提供待审核计数。
- 卡片至少有“保留摘要”“重新生成”两个按钮；建议另有“查看正文差异”作为辅助，但不是首版硬依赖。
- 待审核摘要在自动召回/注入阶段不能静默作为已确认当前事实使用；未来 T-09 应按策略决定阻止该摘要或降级，不由 Stage-B 搜索页提前实现。
- delete/reorder/复杂分支变化仍按各自更严格流程处理，不套用“小编辑默认保留”的便利规则。

## 5. 与现有契约的关系

现有契约继续成立：正文 edit 产生不可变 Revision；派生输出保存原始 input_refs/provenance；来源变化不能靠改旧引用伪造“重新生成”。

新增点只是把“来源变化后怎么办”从自动重建改为**显式人工审核分流**：
- 未审核：L0 needs_review，上级 blocked-by-review；
- 用户保留：记录版本化兼容确认，原摘要内容与上级依赖可继续；
- 用户重生成：创建新 L0，实际依赖旧 L0 的上级按依赖链失效并由用户逐层重建。

实现前需要为兼容审核记录设计最小持久结构和导出/恢复语义，但不需要引入语义相似度模型或自动判断“这次是不是小改”。
