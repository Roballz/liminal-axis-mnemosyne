# 核心库体积与历史增长

1.4.38 修复新写入中的两类额外膨胀；旧库、旧视图、摘要内容及来源身份保留。实现和合成验证不代表用户真实资料已经完成测量或整理。

## 楼层数不能单独决定备份大小

核心包包含整个活动库：全部故事和分支、仍保留的正文与版本、摘要、来源凭据、历史选择视图、事件和表格历史。最长聊天的楼层数只是其中一个维度。正常 `forkBranch()` 复用原正文 message/revision 引用，不把正文按分支数简单重复；独立归档相同聊天则可能形成独立身份。不能根据“十个分支”直接断言正文复制了十遍。

## 已修复的增长机制

### 混合层级摘要的排序编号

宿主同步按 L0、L1、L2 层级枚举摘要。旧实现把数组位置当作持久排序编号，新 L0 插到高层之前时，未改内容的高层条目也全部变号，触发其所在叶桶及祖先重复写入。历史视图需要旧节点，重复数据因此累计，重新接近二次增长。

新实现使用 schema 2 已支持的稳定安全整数。成员追加或删除时保留旧编号，新增成员占用预留间隙；真正重排或间隙用尽时只重新分配必要部分。所有视图物化后的精确枚举顺序保持一致；历史视图和节点不改写。

相同生产发布函数的合成模型：每 2 楼一条 L0，每 8 条 L0 一条 L1，每 5 条 L1 一条 L2，只计算累计视图和选择节点的 JSON 体积。

| 楼层 | 修复前 | 修复后 |
| ---: | ---: | ---: |
| 1,000 | 13.41 MiB | 1.73 MiB |
| 1,980 | 49.80 MiB | 4.65 MiB |
| 5,000 | 296.70 MiB | 9.53 MiB |
| 10,000 | 1,290.73 MiB | 19.94 MiB |

此表不含正文、摘要内容、事件或表格，不能把最后一列当作用户完整核心包的预测大小。测量使用内存假事务；累计体积包含所有历史写入，未通过删除历史降低数字。脚本为 `scripts/benchmark-summary-growth.cjs`，原始对照在 `evals/core-package-growth-1.4.38.json`。

### 分支继承共享旧依赖

旧复制路径在异步读取前检查是否复制过，读取后缺少再次确认。共享图的多个路径可同时通过检查，导致同一旧修订重复复制。真实 `forkBranch()` 合成回归中，8 层共享图原应复制 33 条，旧代码实际复制 527 条。

修复后在读取返回时复查预留身份，在递归前登记身份，并使摘要与表格复用同一历史副本。没有把未选中的历史摘要提升为当前选择，也不修改父分支。该修复阻止未来重复，不能自动认定旧副本可删除。

## 旧数据和其他增长项

早期完整摘要选择映射、已经生成的重复索引、旧版内嵌正文及已有审核仍保留。没有高层摘要覆盖时，摘要依赖列表也可能越来越长；对前缀摘要逐条“保留审核”可留下较长来源数组。这些不应通过盲目删历史、摘要或审核来压小文件。

历史视图没有可靠的创建顺序字段，不能把随机 ID 排序当作时间线。未来无损整理需要验证每个旧视图的 family/revision 和枚举顺序完全一致，并精确处理节点引用；更稳妥的方式是生成独立新库、完整验证后切换并保留原库。本次没有自动执行此类整理。

## 本地只读体积统计

“档案 / 迁移 → 数据包边界与恢复 → 分析核心包体积”按 store 每批最多 128 行读取，批间结束事务并让出执行机会，不持续持有全库只读锁，不在 UI 线程解析整包。仅用户手动触发，没有后台轮询。

结果列出记录数、JSON UTF-8 字节数、旧完整视图、节点条目、审核来源、摘要依赖、旧正文及快照引用的累计数量。复制报告只包含数字和固定类别名，不含聊天正文、摘要文本、档案名、实体名或身份 ID。它是带时间的诊断统计，不替代完整备份一致性校验；页面或公开归档版本变化时取消。

## 容量上限的作用

512 MiB 是本版本的单文件处理门槛，用于容纳用户已存在的 270 多 MB 包。修复增长机制与提高门槛分别解决新数据的额外重复、当前大包不能保存的问题。有限门槛不是无限容量或手机低内存承诺；正文及有效历史继续增加仍需空间，20 份自动文件也会放大磁盘占用。

完整备份仍有整包对象和校验成本。进一步扩展到非常大的库，需要在实际体积组成基础上评估无损整理、分块或流式备份，而不能仅凭楼层数承诺任意大小。具体大包验证与未验证范围见 [v1.4.38 回执](../notes/v1.4.38-core-package-size.md)。
