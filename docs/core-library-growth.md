# 核心库体积与历史增长

1.4.38 修复新写入中的两类额外膨胀；旧库、旧视图、摘要内容及来源身份保留。实现和合成验证不代表用户真实资料已经完成测量或整理。

## 楼层数不能单独决定备份大小

核心包包含整个活动库：全部故事和分支、仍保留的正文与版本、摘要、来源凭据、历史选择视图、事件和表格历史。最长聊天的楼层数只是其中一个维度。正常 `forkBranch()` 复用原正文 message/revision 引用，不把正文按分支数简单重复；独立归档相同聊天则可能形成独立身份。不能根据“十个分支”直接断言正文复制了十遍。

## 已修复的增长机制

### 混合层级摘要的排序编号

宿主同步按 L0、L1、L2 层级枚举摘要。旧实现把数组位置当作持久排序编号，新 L0 插到高层之前时，未改内容的高层条目也全部变号，触发其所在叶桶及祖先重复写入。历史视图需要旧节点，重复数据因此累计，重新接近二次增长。

新实现使用 schema 2 已支持的稳定安全整数。成员追加或删除时保留旧编号，新增成员占用预留间隙；真正重排或间隙用尽时只重新分配必要部分。所有视图物化后的精确枚举顺序保持一致；历史视图和节点不改写。

相同生产发布函数的合成模型：每 2 楼一条 L0，每 8 条 L0 一条 L1，每 5 条 L1 一条 L2，只计算累计视图和选择节点的 JSON 体积。

### 分支继承共享旧依赖

旧复制路径在异步读取前检查是否复制过，读取后缺少再次确认。共享图的多个路径可同时通过检查，导致同一旧修订重复复制。真实 `forkBranch()` 合成回归中，8 层共享图原应复制 33 条，旧代码实际复制 527 条。

修复后在读取返回时复查预留身份，在递归前登记身份，并使摘要与表格复用同一历史副本。没有把未选中的历史摘要提升为当前选择，也不修改父分支。该修复阻止未来重复，不能自动认定旧副本可删除。

## 旧数据和其他增长项

早期完整摘要选择映射、已经生成的重复索引、旧版内嵌正文及已有审核仍保留。没有高层摘要覆盖时，摘要依赖列表也可能越来越长；对前缀摘要逐条“保留审核”可留下较长来源数组。这些不应通过盲目删历史、摘要或审核来压小文件。

历史视图没有可靠的创建顺序字段，不能把随机 ID 排序当作时间线。未来无损整理需要验证每个旧视图的 family/revision 和枚举顺序完全一致，并精确处理节点引用；更稳妥的方式是生成独立新库、完整验证后切换并保留原库。本次没有自动执行此类整理。

## 本地只读体积统计

“档案 / 迁移 → 数据包边界与恢复 → 分析核心包体积”按 store 每批最多 128 行读取，批间结束事务并让出执行机会，不持续持有全库只读锁，不在 UI 线程解析整包。仅用户手动触发，没有后台轮询。

结果列出记录数、JSON UTF-8 字节数、旧完整视图、节点条目、审核来源、摘要依赖、旧正文及快照引用的累计数量。复制报告只包含数字和固定类别名，不含聊天正文、摘要文本、档案名、实体名或身份 ID。它是带时间的诊断统计，不替代完整备份一致性校验；页面或公开归档版本变化时取消。

## 容量上限的作用

512 MiB 是本版本的单文件处理门槛，用于容纳用户已存在的 270 多 MB 包。修复增长机制与提高门槛分别解决新数据的额外重复、当前大包不能保存的问题。有限门槛不是无限容量或手机低内存承诺；正文及有效历史继续增加仍需空间，20 份自动文件也会放大磁盘占用。

完整备份仍有整包对象和校验成本。进一步扩展到非常大的库，需要在实际体积组成基础上评估无损整理、分块或流式备份，而不能仅凭楼层数承诺任意大小。具体大包验证与未验证范围见 [v1.4.38 回执](../notes/v1.4.38-core-package-size.md)。

## 1.4.39：显式无损整理

档案 / 迁移 → 数据包边界与恢复 → **无损整理到新库**。这是用户主动触发的独立库重编码；不自动运行，不直接重写原库。全部故事、分支、修订身份和来源身份保留，旧摘要版本、审核、事件及表格历史保留。整理后再导出的核心包采用 v17；1.4.38 及更早版本不能读取 v17。数据库新增空 store 的升级版本为 6。

### 存储方式

- `memory_revisions` 的长文本、inputRefs、coverage、dependencies，以及 reviews 的长来源/覆盖/依赖列表可以引用 `memory_payloads`。短字段继续内嵌。分支修订仍保留自己的 ID；仅完全相同的载荷共享，没有用文本相等替代来源身份相等。
- 列表按 64 项分叶块、64 子块分内节点；保留原顺序、重复项及精确 ID。同步路由摘要只用于查找候选，每次复用检查完整内容，碰撞分配后缀。单列表最多一百万项、读图深度最多 12；超限会停止整理/导入，原库保留。
- 所有历史选择视图重新编码为稳定序号的共享树，相同内容节点复用。旧 view ID 不改。随机 view ID 的枚举次序只提供压缩前驱候选，不作为历史时间线；每份视图都验证 family/revision 及枚举顺序相同。
- 新库有版本化共享存储标记；之后正常摘要、分支继承、审核写入也继续共享。读取时透明展开；证据根统计、正文回收和档案删除基于展开后的引用。删除产生的无引用共享块不会自动 GC，再次手动整理会重编码仍有引用的内容。

### 整理及切换保护

后台 Worker 每批最多 32 行，事务间让出执行机会；视图逐份处理，跨事务只保留一个压缩前驱。共享块缓存按 256 块 / 512,000 个 JSON 字符限制，并合并同一事务内尚未返回的相同块读取。进度同阶段最多每 200ms 通知一次，不触发聊天/事件全量刷新。

复制后逐页核对全部逻辑记录，逐个核对历史视图，检查目标记录数，依次运行原库及新库的完整领域校验。全部表的成功写事务更新内部持久标记，整理期间任何连接写入都会取消切换。最终在阻挡写入的只读事务内核对标记并同步发布活动库选择，避免最后一次检查与切换间漏掉写入。归档同步沿现有 activation 队列排空。

失败、退出页面或资料变化时原库保持活动；已写的新库保留且不自动清除。重新点击会从头生成另一独立库，当前未实现断点续做。成功后只刷新一次当前投影，建议导出新的核心包保存。需要原库与新库共存的额外空间；原库保留不表示本机占用立即下降。回退可用整理前保存的核心包，通过既有恢复入口写入独立库。

完整领域校验/导出仍会在 Worker 内构造完整包；它不是全程常量内存或流式备份。体积统计按物理字段统计，整理后列表引用与内容块计入 `memory_payloads`，原 details 中数组条数/字节只含仍内嵌的数组，不能据此判断逻辑依赖丢失。真实缩小比例取决于重复率，不能由楼层数预测。

合成 400 个摘要身份 × 20 版（8,000 条修订）、972,800 次依赖引用：记录 JSON 合计 72,340,934 → 5,375,107 字节；独立导出/恢复完全一致。该样本高度重复，不代表真实用户核心包。结果与运行边界见 `evals/core-reorganization-1.4.39.json`；Node 脚本为 `scripts/benchmark-core-reorganization.cjs`，独立浏览器测试页为 `evals/core-reorganization-responsiveness.html`。


## v1.4.40：历史重复摘要身份与分支继承

早期分支复制会为同一宿主摘要留下多个 family，其中部分仅服务表格历史证据。同步必须优先使用当前选择的 family，不能按数据库枚举顺序选最后一个。无选中项的重复历史不自动冒充当前身份。

已有分支若被旧同步误选，可用当前高层总结依赖和事件引用寻找原继承修订；仅在摘要指纹、内容、层级及正常来源/审核/依赖校验全部匹配且不存在冲突候选时恢复选择。不会改写原文、摘要、父分支、审核或表格历史；真实修改及歧义仍待确认。恢复写入普通 MemoryView，不新增包格式。仅有重复 family 的继承分支需额外检查，按相关选择状态做有限内存缓存，事务提交后才记忆结果；日常追加不反复扫描事件历史。
