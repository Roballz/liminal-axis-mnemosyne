# T-02 候选方案：版本化历史与 B → A 可迁移架构

状态：**proposed，待用户讨论确认；不是正式 T-02 任务卡或已冻结 schema。**

日期：2026-09-19。Mnemosyne 阅读基线：`7bf7375616ccd5227f18f67544b686b1c4081a14`。本轮公开 TT 来源固定为 `a1855be4a4f8b6ee7cd0374a84dbb3709c3e5375`；其新增数据库能力没有在本轮于用户设备上执行验证，不把源码可用等同于现装版本可用。

## 1. 阶段定位与已确认约束

T-00、T-01、T-02A 已 review 通过。T-02 当前要冻结数据身份、历史版本、分支、派生来源与上下文契约；T-03 才决定经过恢复/性能验证的实际存储 provider。S-A 最终完成线仍是接入、核心契约与可恢复存储三者闭环；采用本机 B provider 时需明确调整 T-03 的部署验收，不把服务器 A 版默认为已经完成。

保留用户已经确认的需求：

- 续接旧剧情必须由用户显式选择；普通新聊天不自动继承旧记忆。
- Story/Branch 与宿主聊天文件解耦；跨文件续聊不等同剧情分叉。
- 普通摘要/记忆按一轮 User + Assistant 共同生成，默认不为 User 楼单独生成记忆。
- 原文档案与派生记忆分离；不覆盖唯一原文。原文按消息保存，不等于每条 User 消息都单独摘要/embedding/注入。
- V1 为上帝视角、多角色世界，不按某角色是否知情过滤普通剧情记忆；故事/分支/截止点、用户明确排除及实际发送许可仍有效。
- 可导入只有摘要的旧记忆，明确无原文，不伪造引用。
- 身份/版本不确定时不猜测合并，保留用户手动映射与修复。
- B=依托 TT 本机持久化的部署方式；A=独立服务器部署方式。它们不是 S-A/S-B 阶段编号，也不应变成两套不兼容领域模型。

## 2. TT 已有能力：三套不同模块，不混为一个记忆系统

以下为固定 TT 提交的文档/接口事实，不是本轮真机测试结果。

| 模块 | 已提供 | 对本项目的价值与边界 |
| --- | --- | --- |
| 内置 Summarize | 摘要写入 `message.extra.memory`，沿用扩展 prompt 注入 | 可参考宿主接入；不是本项目完整分支版本、派生依赖和失效模型；本方案不要求用户启用它 |
| Vector 兼容层 | 原生 redb 索引、embedding 接口、dense 与有界 lexical 的 RRF 混合、按聊天顺序注入 | 可参考 provider/profile 隔离、批次完整写入与检索组织；不等于 TriviumDB；文档明确聊天 lexical 最多扫描近期 1000 条，不直接作为千万字全档检索 |
| `api.db` / TriviumDB 0.8.8 | 原生 JSON payload、向量、文本、图关系、TQL、落盘与 namespace 数据维护 | 可作为 B provider 候选；没有替 Mnemosyne 定义 Story、Branch、Revision、每轮派生与分叉记忆有效性 |

数据库可以存关系，不代表它已知道剧情因果；高级检索中的 rerankK、扩散/抑制开关也不能直接等同于用户配置的外部 reranker 或可靠剧情记忆规则。初始基线建议显式采用可解释的检索设置，高级机制独立对照实验。

### 对 B 版必须保留的实际限制

1. `indexText/indexKeyword` 手工文本索引不进入 WAL；`syncMode=full` 不能改变这一点。必须保存重建所需源文本，测试 `buildTextIndex` 与重开后的恢复。
2. API 声明 `batchInsert` 整批原子提交，但公开 handle 没有一个任意多调用的通用 transaction/CAS 接口。不能把多次 insert、link、更新 head 的成功分别相加，假定整体原子。
3. 标准 insert/upsert 带 vector，namespace 固定向量维度。原文/版本存储不能要求先付费 embedding，也不能因换 embedding 模型损失原文；T-03 必须验证合理的无语义向量记录路径或独立持久化路径，不先承诺一个库包办所有数据。
4. `NodeId` 是宿主安全整数，`listNamespaces()` 只列当前打开的 namespace。Mnemosyne 需有自己的可持久化 ID 映射与导出目录；搜索 topK 不能代替完整记录枚举。
5. TT 当前数据库同步按整个 namespace 替换或保留，**不合并记录**；默认同步范围不含数据库，Full 才包含。设备双边独立写入后互相覆盖有丢更改风险。
6. namespace 提供物理分组，不是同一 WebView 内扩展之间的安全沙箱。设备备份、模型密钥与本机模块发送许可需另行处理。

## 3. 推荐的总模型：不可变正文版本 + 分支历史清单 + 可重建索引

推荐吸收版本控制的快照/引用思想，但不直接用 Git 存用户剧情，也不为 V1 自建完整 Git、分布式事件溯源或多主 CRDT。

### 3.1 对象职责（名称为候选）

| 对象 | 表达什么 |
| --- | --- |
| Story / Branch | 故事归属与当前剧情线 |
| HostBinding / Segment | 哪个 TT 聊天承载哪条剧情线及其中哪一段；保存宿主实例/账户范围、kind、stableId 与可变 ref |
| SourceMessage | 一条逻辑消息的 Mnemosyne 身份，不以楼层号或文本 hash 当主键 |
| SourceRevision | 该消息某一版实际原文和来源信息；已提交版本不原地修改 |
| HistorySnapshot | 某个历史状态的有序清单：每条 SourceMessage 选用了哪一版 SourceRevision |
| Branch head | 指向本 Branch 当前采用的 HistorySnapshot；末尾楼层是另一个定位信息 |
| TurnMemory | 通常由本轮 User 与 Assistant 的实际版本共同生成的一份摘要/抽取结果 |
| Event / Record / StateChange | 跨段事件、实体档案与状态变化；均有可追溯版本与依赖 |
| ContextBlock | 某次生成临时组装的注入块，不直接等同永久数据库记录 |

Mnemosyne 主 ID 使用独立 UUID 一类标识；具体生成规范由 T-02 冻结。TT stableId、文件名、楼层、Trivium NodeId 只在适配/存储映射层使用。已经有明确绑定时可以自动定位；不能因拿到了一个宿主 ID 就把任意导入文件强制并入现有故事。

### 3.2 父线改旧楼，不需要自动开 Branch C

例：父线和子线都引用消息 M20 的 R1。父线改写后创建 R2，父线的新历史清单指向 R2，子线仍指向 R1。其他未改变正文和可复用记忆不复制。

关键不是“实时读取 parent 最新历史直到第 50 楼”，而是“读取 fork 当时固定的历史快照前缀”。分叉记录固定的父 snapshot 与包含端点的 cutoff；同一条消息在不同分支可选择不同 revision。

快照在逻辑上是完整历史，不要求物理上每轮复制整个列表。实现可选择分块共享目录，或有检查点的有界增量；在 T-03 测冷启动、深分叉、深层编辑后的读写成本，避免每轮完整序列化千万字或无限回溯祖先。

V1 暂不推荐自动合并两条剧情分支。跨线搬运事实应是明确的用户动作，而非版本控制式文本自动 merge。

## 4. 身份重识别：有依据自动化，无依据让用户选择

### 4.1 首次导入

用户明确选择新故事、绑定已有剧情线、分支或续接。保存原始备份/来源证明，生成内部 ID 与有序映射。允许用易读名称选择目标，不要求用户手填 UUID。

### 4.2 后续匹配的证据优先级

1. **本系统逻辑导出包**：先校验 schema、内部 ID、内容校验和与引用完整性；同 ID 内容冲突不能覆盖。
2. **已绑定宿主聊天 + 已知操作**：结合 stableId、kind、绑定作用域、上次确认映射与此次 edit/swipe/regenerate 等操作定位；处理前后仍校验内容与顺序。
3. **已知映射中精确不变/精确追加的部分**：保留原 ID，只导入新增后缀；相同原文重复出现时不能跨条目合并。
4. **缺少可靠绑定的旧 JSONL**：文件指纹、消息角色、正文、顺序前缀、宿主 metadata 作为候选证据，必要时做有界序列对齐；歧义部分人工确认。

内容相同只说明相同内容，不证明相同历史身份。旧 JSONL 没有保存的编辑/swipe 历史不能恢复为“已知版本”；仅记录当前可得信息与未知范围。

副本含多个相同“好”、删除后插入相同文本、相同 integrity 的手动复制档，均不应靠位置+hash 强行唯一解释。已确认相同导入批次可无操作完成；有意复制为独立故事属于新操作。

### 4.3 B 版降低操作负担的建议

默认使用独立映射记录，不把整份记忆塞进消息 `extra`。未来可研究用户授权写入小型 Mnemosyne 绑定/消息标签，但不是当前任务的隐式写入许可；复制/分叉会一起复制标签，仍需校验宿主绑定与分支用途，标签不是万能唯一性保证。

## 5. Edit / Delete / Regenerate：事件提示变化，稳态校验后提交

T-02A 已验证的宿主事实继续适用：Edit/Swipe 可观测；Delete 参数为删除后长度；成功 Regenerate 可走删除/重建且候选数不增；summary 与 context 在过程中可暂不一致。

推荐：事件一到就令本轮未应用的上下文准备失效，记录受影响范围；后台读取稳定状态后，形成一个明确历史变更提交。不要把每一个宿主中间事件直接解释成领域永久删除。

- **Edit**：同一已匹配消息产生新 revision。已知事件处理目标，重新打开/恢复/漏事件时再对账。
- **Delete**：对照上次确认的指纹/映射与当前有序消息，识别消失项与索引移动；一轮局部校验不够则有界扩大，仍歧义则暂停并人工修复。不得每 token 全档扫描，也不得只按最高楼层裁掉尾部记忆。
- **Regenerate**：在已知生成操作内合并删除/重建观察，成功稳态再更新当前选择。失败/空结果保留失败记录，不把 `GENERATION_ENDED` 或 `MESSAGE_RECEIVED` 单独视为成功。它是否沿用 SourceMessage 身份由操作关联和已确认映射决定，不由 index 相同直接决定。
- **漏事件与外部编辑**：打开聊天、恢复运行、导入或显式核对时做受控校验。稳定 ID 不能证明正文没变化；普通 UI 事件通过也不等于所有外部改文件方式都可实时侦测。

即使宿主丢弃旧候选，Mnemosyne 也可保留先前已实际采集的旧版本；不能声称保存过从未读到的候选。一次删除后仍被其他分支引用的原文，不可仅因父线删除就清理。

## 6. 回合记忆、来源依赖与分支安全

普通情况下只生成一份 User + Assistant 的 TurnMemory；底层保留两个原文版本引用是为了精确定位/重建，不额外产生 User 独立摘要费用。User 中的“请让下一幕发生……”属于指令，不自动当作已经发生的事实；与 Assistant 正文共同提取时要区分要求、已发生内容和正文有据的心理状态。

候选显示名可为“记忆印记”，技术名先用 TurnMemory；Event、Record 保持含义清晰，正式品牌命名另行确认，不沿用 Leaf。

### 必须分开的两类依赖

- **证据来源**：这条事实在哪些消息/记忆版本中有依据。
- **生成依赖**：生成它时实际读取了哪些历史上下文、状态与规则；不一定都在摘要中被引用。

只追踪最终引用而漏掉生成依赖，会让“引用没变、实际依赖已变”的记忆继续误用。局部回合摘要建议使用有界输入，跨段事件/状态另保存依赖，以控制深层编辑重算范围。

### 共享记录的有效性必须相对于分支判断

不能在共享记忆上写一个全局 `invalid=true`：同一 R1 记忆在改到 R2 的父线中不再适用，在仍选用 R1 的子线中可能完全有效。结果发送给模型前，需检查目标分支当前所选版本、来源截止点、依赖、用户排除与发送许可。

**分叉在 User 楼的例子：** 若一份 TurnMemory 使用了 User #100 和 Assistant #101，而子线截到 #100，它不能继承这份完整摘要。完整来源/依赖都位于子线历史范围内才可复用；不能为了省一次摘要而泄露 #101。事件横跨 fork cutoff 时也不能继承父线后来更新的“最终结果”记录。已发生前缀可重新构建相应事件版本，或等待补齐后再生成。

开场白、Continue、多个连续 User/Assistant、群聊等非标准配对仍需定义例外规则；不得为满足 1:1 结构虚构 User 或把错误配对写入。这个例外讨论不改变普通情况下“一轮一份摘要”的已确认体验。

明确导入的 derived-only 记忆与损坏的悬空引用不同：前者可召回但不能展开原文，后者进入 needs-resolution。无法自动重算的无原文条目需用户/助手修订，不能伪造原文补齐。

## 7. Head、运行身份与哈希：分别回答不同问题

| 概念 | 回答 |
| --- | --- |
| History snapshot / head | 当前采用哪套有序正文版本？深层编辑也必须变化 |
| Run ID | 这次准备注入属于哪一次生成？相同输入重试仍可有不同 run |
| 原文/内容 hash | 内容是否一样、传输是否完整？不证明消息身份 |
| 派生输入指纹 | 同一来源版本、实际上下文依赖、模型/提示词/schema/参数下的同类工作是否已做？ |
| 幂等操作键 | 这是不是同一次提交的网络重试？同 key 不同 payload 必须冲突 |

建议采用版本化的规范 JSON 编码与 SHA-256 一类内容校验方案；原文原样保存。canonicalization 规范序列化，不擅自删除正文空格、变更 Unicode 或用剧情时间排序来认定“同一历史”。模型别名/服务端行为可能变化，应记录已知 profile 与版本限制，不以 hash 保证模型每次输出一样。

生成准备请求捕获宿主绑定、当前 history head、run、输入与策略/记忆选择版本；最后应用注入前复核。变化则丢弃/重新准备。宿主事件已发生但正式历史尚未完成提交时，也应先令待应用结果失效，不能等异步落库才发现。

后台摘要与本轮上下文采用不同有效性检查：历史继续追加不一定使已经生成的旧回合摘要失效，若其实际来源/依赖未变仍可复用；不能把“head 变了”机械套用于所有后台任务而导致永远无法完成。

## 8. B 先行，但只有一套 Mnemosyne 规则

建议组织为可复用 Core、Host Adapter、Canonical Store、Search Provider 与 Workbench，而非 B/A 各写一套业务。

B 中 Core 由 TT 扩展驱动，本机 provider 访问 TT 原生持久化/检索；A 中同一套领域规则可运行于服务器，由远程 API 提供服务。改变的不仅是数据库地址，还包括执行位置、任务恢复、认证、网络失败和维护生命周期，因此需要共享契约测试，不能承诺迁移零代码。

### 建议 B 的第一版运行约束

**同一记忆库同一时刻只有一个权威写入端。** 手机/电脑切换用明确交接；不实现离线双写后自动合并。TT 的 namespace 整体同步本身不是分布式写锁，无法防止两台离线设备各自改同一库。若用户需要同时编辑或无缝多设备，应提前提升 A 的优先级，而非把整库覆盖包装成安全双向同步。

本机摘要/索引任务在 TT 关闭或被移动系统终止时可能中断。任务进度应持久化，重开后按依赖与幂等规则续作；不能假装 B 提供永不中断的服务器后台服务。

### 建议 B 的持久化验收底线

- 原文、版本、分支目录与元数据可以不依赖 embedding 成功而保存。
- 一个业务变更发布后，其 head 不得指向半写入对象；检查断电/崩溃、重试与恢复，不仅测试正常 flush。
- 若无跨调用事务，则验证单写者下“先持久化不可变对象、再发布完整历史提交”的恢复协议；这不等同已有通用 ACID 事务，也不替代失败注入测试。
- 精确内部 ID 查询、完整逻辑枚举/分页、引用完整性与导出可实现且成本可接受；不依赖向量近似匹配找主键。
- 文本/向量索引落后时，正式源数据仍完整且旧分支/旧版本不得被误注入；索引可从正式数据重建。
- 百万字真实集验证质量，5x/10x 合成数据验证容量、冷启动与恢复；分别标注，不能以复制文本证明真实长剧情召回质量。

## 9. B → A 迁移：先一次性交接，不先造双向同步

候选流程：暂停 B 的正常写入 → 生成逻辑导出包 → A 暂存导入并校验 → 重建索引/复核样本 → 切换权威 provider → 保留 B 只读回退副本。

迁移包应保留内部 ID、原文版本、历史快照/分支引用、宿主绑定与来源、派生记忆及依赖、事件/档案/模块、用户人工修改/锁定、删除隔离状态、策略/schema 版本与必要任务检查点。密钥不作为普通包输出；明确 local-only 模块需遵守用户选择，不能因迁移自动上传。

已存在的摘要、实体档案和事件是要搬走的正式数据，**不因更换 provider 就重新调用 LLM 总结全部剧情**。embedding 和物理索引可重建；同模型/同预处理/profile 的向量是否复用另验证，不把 vendor NodeId 带成正式 ID。

校验不仅是记录数量，还要检查校验和、引用存在性、每条 Branch 的有效历史、人工修改、失效/删除排除及代表性召回结果。B 版先完成逻辑导出 → 空环境重建演练；A 可用后做 B → A 对照演练。

切换后只让 A 接受正常写入。若 A 已产生新剧情，回退需先迁回/保全 A 增量，不能直接打开旧 B 副本写入而丢掉后续进度。迁移触发由实际性能/跨端需求和 A 成熟度决定，不以“到千万字那天”作为唯一条件。

## 10. 需要用户确认的产品选择与仍需实验项

本轮不是要求用户选择算法。需要确认的是可感知的取舍：

1. 父线改旧历史时保留旧版本，子线不跟随变化；不自动创建新剧情 Branch。
2. 可靠证据自动映射；旧档歧义弹出可读差异，让用户选择，不靠 AI 猜测历史身份。
3. 普通一轮一份回合记忆，原文消息分开归档；非标准回合和跨 cutoff 的边界明确处理。
4. B 优先但先约束为单权威写入端，迁移先停写交接，不做离线双主自动合并。

仍需工程攻坚：有界序列对齐/歧义处理、分支快照目录成本、依赖失效传播、提交原子性与恢复。技术方案由 Chat/实现验证承担，用户不必凭空选择底层数据结构。

原 24 项对应：1～3 为 Story/Branch/绑定；4～9/19～21 为身份与宿主对账；10～12/17 为快照与有效历史；13～14/22 为派生来源/回合与缺失原文；15～16/18 为上下文运行/指纹；23 保持 V1 上帝视角，24 为有范围的冲突隔离与修复。ContextBlock 完整字段、对象最终命名、非标准回合、保留/清理周期仍待后续讨论，不宣称 24 项全部冻结。
