# RP 记忆系统：架构与实施基线

**版本：v0.1｜日期：2026-09-17｜状态：设计草案，可迭代，不是已实现产品**

文档所有者：球球。首个宿主：TauriTavern（TT）。现有参照：Roballz/ST-BaiBai-Book（柏宝书）。目标：从千万字起步，面向亿字级原始档案设计；具体性能必须实测，不承诺无限规模、完全不漏召回或模型永不遗忘。

本文件是架构主文档。开发任务见 `02-roadmap.md`，未决项见 `03-decisions-and-open-questions.md`，协作流程见 `04-working-with-chatgpt-codex.md`，外部证据见 `05-source-review.md`。示例不是完成的实现或冻结的 API。

## 0. 如何使用这份基线

文档采用四种状态，避免编码助手把讨论当成用户批准的决定。

| 标记 | 含义 | 对开发的约束 |
| --- | --- | --- |
| U：用户明确需求 | 用户已表达的目标与约束 | 不得擅自删改；有冲突时提出变更 |
| B：建议基线 | 本版提出的默认架构 | 可用于原型；不代表用户逐条批准 |
| E：实验项 | 有多个合理解法 | 做对照测试后再确定；保留可替换边界 |
| D：延后讨论 | 本次刻意不定案 | 只预留接口，不提前实现复杂方案 |

“U”确认的是需求，不是“代码已经实现”。本版没有部署服务、修改现用柏宝书、创建远程 GitHub 仓库或导入用户真实聊天。

### 0.1 本轮范围

本轮明确前后端边界、原始档案与派生记忆的关系、常驻／激活／注入策略、自定义模块、助手修改流程、TT 接入与渐进迁移路线。

长剧情如何生成全局骨架、L1～Ln 如何常驻、跨千万字如何保持因果连续，列为 D。这里仅设保护性约束：不能用删除原文和底层证据来换取提示词变短；存储历史与每轮注入必须分开。

## 1. 产品目标与非目标

### 1.1 用户明确需求（U）

原始聊天与记忆要归用户所有，支持自托管 VPS／远程服务器、可导出和迁移。TT 是当前入口，但数据库与领域逻辑不能绑定 TT。

保留“每楼叶子摘要；相关时升级为原文”的体验。自动召回方向为 Vector + BM25 + RRF + Rerank，同时支持人物、物品、地点、组织、设定等精准查询与模糊激活。

人物与物品不因身处远处而失去展开资格。需要重点详情常驻、次级概览常驻、隐藏但可召回；隐藏不等于删除或永不激活。

前端可创建自定义记忆模块和字段，例如【记忆残响】；可由副 API 填表、整理和修改。模块允许本地使用，不强制进入远程后端。

前端助手允许手动调用副 API 做新增、重写、修正和建表。不同记忆类别的注入角色、位置、深度需要独立配置。长期稳定内容放历史前，动态召回可放 user @d0 或 system @d0。

### 1.2 不在首版做的事情（B）

不重写完整 RP 聊天应用，不重造角色卡／世界书／预设全部生态；不把 MCP 作为启动前提；不让前端扫描全量远程向量；不让副 API 自由执行 SQL、脚本或删除档案；不承诺跨平台提示词位置自动完全等价。

## 2. 当前参照与实现核验（F：外部事实）

本次检查柏宝书提交 `32dbb48a0a643804256d496bc35bf7699dea9ebe`。这是用户提供的 Roballz 仓库，不自动等同原作者仓库或用户手机安装包。

**检索实际路径。** `src/memory/vector/index.ts` 把叶子摘要作为向量化文本，另存楼层原文；`recall.ts` 的 rerank 优先使用原文，缺原文才用摘要。最终高于 rerank 阈值的候选可升级全文，其他候选还受 embedding 阈值影响。[B01][B02]

**本地后端边界。** `store.ts` 已有存储接口：检测到柏宝库时转发后端，否则使用 IndexedDB 本地实现。本地搜索读取 scope 下记录，用多条查询的最高余弦分数合并并截断；本地 bundle 能力有限。[B03]

**文档与代码差异。** FAQ／部分注释提到 RRF 或后端必装，但上述本地实际搜索使用 max 融合，且有本地回退。首轮改造要核对安装版本，不能直接根据 FAQ 判断当前算法。[B02][B03][B06]

**现成迁移入口。** 公开 `STBaiBaiBook` API 有快照、单楼、历史和变更订阅，返回只读 DTO，并提供覆盖不完整提示。它适合初期只读桥接；不是公开写接口，修改返回对象不会写回柏宝书。[B04]

**TT 边界。** 当前公开 API 文档提供 chat、layout、扩展存储等能力，MCP 仍列为规划；ChatPayload 文档明确当前聊天完整加载、完整保存，历史分页是独立读取能力，不等于活动聊天按需加载。[T01][T02]

这些结论来自源码／文档检查，并未在用户设备联调。TT Adapter 第一项工作仍是固定安装版本，验证网络、异步拦截、注入顺序和失败行为。

## 3. 总体架构（B）

采用“独立记忆服务 + 可复用管理界面 + 薄宿主适配器”。首版按模块化单体组织，不先拆成大量微服务。

```text
TT / 后续其他宿主
  └─ Host Adapter：消息事件、身份映射、生成拦截、注入、UI 挂载
       ├─ Workbench：档案管理、检索调试、自定义模块、助手、同步状态
       ├─ Local Store：离线待同步队列、本地模块、有限缓存
       └─ HTTPS Memory API
            ├─ Archive：原文、消息版本、故事分支、导入与导出
            ├─ Records：实体档案、状态变化、自定义模块
            ├─ Derivation：摘要、抽取、索引、失效与重建任务
            ├─ Retrieval：词法、向量、融合、重排、事件扩展
            └─ Context：激活规则、证据、预算、注入块规划
                 ├─ Canonical Store：事实与来源的正式存储
                 └─ Search Providers：可重建的检索索引

可选 MCP 门面：复用同一 Memory API / 领域服务，不另建一份记忆。
```

### 3.1 各层职责

**Memory Engine** 管理数据、有效版本、检索和可解释结果；不知道 TT 的 DOM、mesid 或 Rust 命令。所有平台术语在 Adapter 转为系统自己的身份与事件。

**TT Adapter** 只负责宿主连接：获取本轮输入和近期上下文、同步变化、等待召回、应用注入块、清理旧槽、报告最终实际提示词位置。核心排序与档案规则不散落在插件事件回调里。

**Workbench** 是可复用网页组件，可由 TT 插件挂载，也能独立访问。独立管理界面不等于完整聊天前端，不替代 TT 正文生成。

**Context Compiler** 是确定性组装规则：远程服务返回带来源的记忆块，Adapter 合并被允许使用的本地模块，再根据宿主能力、最终预算和位置映射编译。前后端共享规则与测试，而不是各写一套互相漂移的逻辑。

### 3.2 技术选型建议，不冻结具体依赖

建议前后端优先 TypeScript，减少多语言维护；服务端采用成熟 HTTP 框架与模块化结构。PostgreSQL 可作为正式档案／版本／结构化记录存储候选，Qdrant 作为检索候选。最终语言、框架和持久化组合在任务 T-03 用部署与恢复小实验确定。

Qdrant 官方支持 dense／sparse 多路查询和 RRF，但它不是完整 RP 记忆系统，也不会自动替用户选好中文分词、处理实体歧义、剧情版本和注入策略。[Q01]

BM25 的中文分析器、索引对象与实现后端是 E；未完成验证前，不把普通全文检索、字符包含查询或任意稀疏模型标成 BM25。首版不同时引入多个大型搜索服务；选择一个能验证的实现，再保留 Retriever 接口。

## 4. 数据归属：原始档案、记忆、索引分离（B）

### 4.1 正式档案

原始消息保留原貌；清洗后的正文是另一份可重建投影，不覆盖原文。摘要、embedding、实体抽取都保存来源、生成版本和适用范围。

用户显式删除／脱敏是独立操作，必须覆盖相关派生索引与约定的备份保留流程。默认归档不等于不可删除；“删 TT 本地聊天”也不能自动解释为“销毁远程故事”。

### 4.2 最小对象模型

| 对象 | 作用 | 必须保留的关系 |
| --- | --- | --- |
| Story / Branch | 连续故事与版本分支 | 父分支、继承截止点、当前 head |
| SourceMessage / Revision | 用户与模型原文及编辑版本 | 稳定消息 ID、角色、宿主映射、顺序 |
| Leaf | 每楼摘要及其抽取结果 | 来源消息版本、状态、生成模型／提示词版本 |
| Event / EventLink | 跨楼事件与剧情线关联 | 有序证据跨度，可关联多片叶子 |
| Record / RecordRevision | 人物、物品、组织、设定等 | 类型、状态、来源、有效时间与别名 |
| ModuleDefinition / ModuleRow | 自定义模块和记录 | 字段 ID、schema 版本、行版本、策略 |
| StateChange | 某个时间点发生的变化 | 生效顺序、来源、取代或撤回关系 |
| ContextBlock / RunTrace | 本轮注入及诊断 | 使用的版本、来源、位置、token、删选原因 |

楼层号只用于显示和宿主映射，不能作为跨平台主键。改名、分篇和插入消息都不能让原文引用指错。

### 4.3 版本、分支与知识边界

每次召回都带 story、branch、head revision 和截止点，所有检索分支使用同一过滤范围。父分支继承只到分叉点，不可把分叉后的另一结局当成共同历史。

编辑旧楼、切换 swipe、删除或标记番外后，依赖该版本的摘要与状态标记为失效；索引允许异步更新，但结果返回前必须再次检查有效性。不能等索引慢慢刷新期间继续注入错误版本。

故事时间、记录时间、角色获知时间分开。倒叙不等于事情现在发生；作者知道的秘密不等于失忆角色已经恢复记忆。严格不应被模型知道的字段，应在发送给模型前排除，而不是只附上一句“不要泄露”。

### 4.4 正文与派生内容都可缺失

导入只有摘要的数据时，保存 `source_available=false`，不得伪造原文。叶子尚未生成、摘要失败或某段未导入，都显示覆盖状态；不能在界面声称“全库已完整记忆”。

## 5. 叶子与连续事件：先解耦，再优化（B + E）

### 5.1 首版不取消每楼叶子

每楼约 1,000～2,000 字正文、300～500 字摘要是用户当前使用场景，不是本系统永久固定的字数限制。保留每楼叶子，便于补摘、编辑、回滚和原文定位。

检索单位、存储单位和注入单位不必相同。把多楼压成一个大叶子不是唯一解法。

### 5.2 在叶子上方增加“事件关联”，而非再做一次强制压缩

例如三楼分别记录“交出玉佩”“承诺归还”“归还时发现裂痕”。保留三片叶子，另建一个事件记录，保存参与者、物品、事件标题、当前结果及指向三个原文跨度的链接。

同一事件可跨楼；同一楼也可承载两个事件。初版允许手动归组、拆组、排序与修正。自动事件边界识别属于 E，副 API 只提出分组建议，不能悄悄合并原文。

事件 ID 用来组织证据，不证明事件已经完整。记录 `coverage` 和 `status`，例如进行中、结束、边界待确认。

### 5.3 召回后的上下文扩展

先找到相关叶子或原文片段，再取其关联事件中必要的前因／后果。可按来源顺序取邻接片段，或由已确认 EventLink 选择。邻接不等于同事件，跨场景、分支或角色知识边界时停止。

给扩展设置独立 token 上限和最大证据数量。返回“事件标题＋必要背景＋按顺序排列的证据”，而不是每命中一片叶子就注入整章。

候选去重按来源版本／跨度进行；同一事件的多个叶子不能机械全部删成一条，它们可能分别承载关键证据。事件多样性使用可调软配额并保留溢出候选，不能让一条长事件天然占满所有候选。

### 5.4 升级原文需要独立策略

保留“摘要 → 原文”的分级输出，原型先兼容整楼升级；再实验“相关原文跨度＋必要邻接”以减少预算。

升级依据可以组合：真实 rerank 分数、明确原句命中、用户指定需要细节、摘要覆盖不足，以及本轮预算。Rerank 高分表示相关性证据，不代表该事件已经完整或应无上限展开。

当实际 rerank 未执行或失败，`rerank_score=null`。禁止把 cosine / RRF 分数填成 rerank 分数再套用原阈值。必须有显式的无重排降级策略。

## 6. 检索流程：普通剧情与实体查找分路（B + E）

### 6.1 沿用此前讨论的起步方向

保留一次 Query Rewrite 的方向：Vector 使用 Q1～Q5；BM25 使用原始输入、可确定的实体名和关键术语。词法分支可在重写期间先启动，向量分支在重写完成后运行，不为 BM25 再固定多加一次 LLM 重写。

`rerankCandidates=20` 仅作为首轮对照的起始值，来自此前讨论，不是性能上限或已证明最优值。候选条数之外，还限制总输入 token、单文档长度和服务请求上限。

此前关于“先降低 embedding 阈值观察”的结论只针对现用插件排错，不作为新系统固定策略；此前前端 chunks 舒适区估计也不作为本系统容量承诺。

### 6.2 参考流水线

```text
本轮输入 + 少量近期上下文 + 当前有效状态
  -> 身份／分支／截止点／可见性范围
  -> 明确实体或原句查找（确定性分支）
  -> BM25（原文、摘要、可用实体词）
  -> 一次 Query Rewrite -> 向量多 query
  -> 各检索家族内部合并、来源去重
  -> 家族级 RRF -> 有界候选池
  -> Rerank（首轮以原文优先作为参照）
  -> 事件证据扩展／实体详情激活
  -> 有效版本复核、预算、去重、注入块
```

RRF 依据排名融合不同检索分数尺度。[Q01] 多条向量 query 先作为一个检索家族合并，避免五条向量列表天然获得五倍于单条 BM25 的投票权。家族内 max 或 RRF、权重与常数属于 E；记录配置并用测试决定。

### 6.3 不让摘要成为唯一入口

词法索引至少覆盖可用正文投影、叶子摘要、实体标准名与别名。只索引摘要，摘要漏掉的独特词就没有机会靠词法搜索找回来。

原句精准搜索与 BM25 排序分开：精确句子可使用规范化后的短语／字符串校验；大数据下怎样加速该入口单独验证。中文别名使用经过验证的分词或受控字符策略；不因短名字恰好出现在别词里就无条件激活。

语义候选不再全局强制通过旧 embedding 阈值；BM25 独有命中可能 embedding 很低，不能因此被后置阈值全部杀掉。过滤保留来源标签，按任务与证据制定激活策略。

### 6.4 实体不是剧情 chunk 的复制品

姓名／别名明确且无歧义时，可直接激活实体详情，不必与二十段剧情争同一个 rerank 名额。同名、称谓和代词不确定时，返回候选与歧义标记，不自动合并人物。

模糊提及可以由词法、向量或近期上下文激活。地点只是相关性信号，不是强制门槛。关系扩展默认有界，不能提到一个组织就自动展开全部成员与所有物品。

## 7. 展示、常驻、激活、记录：四件事分别配置（U + B）

### 7.1 三种基本常驻模式

| 模式 | 未被提及时的主模型上下文 | 被本轮命中后 | 是否留在存储 |
| --- | --- | --- | --- |
| 重点详情 `detail` | 按已配置字段完整注入 | 不再重复插一份详情 | 保留 |
| 次级概览 `overview` | 一句话概览 | 升级所需详情 | 保留 |
| 隐藏待召回 `none` | 不常驻 | 允许关键词／检索激活 | 保留 |

另设“排除自动使用”开关，不与隐藏混用。界面折叠／隐藏是 UI 偏好；常驻模式控制提示词；`recall_enabled` 控制召回资格；`recording_enabled` 控制是否自动收集新事实。四者不能由一个总开关暗中连带改变。

### 7.2 基本优先级

先执行有效版本、访问范围与角色知识边界，再应用用户排除和常驻策略；然后做本轮激活、详情选择和预算。Pin 不能绕过分支或秘密可见性规则。冲突需要界面提示，不能把隐藏的作者秘密当成普通设定注入。

“重点详情常驻”在指定模型可见字段范围内兑现。预算不足时应明确阻止或请求用户调整，不能悄悄降成摘要却仍显示“完整常驻”。概览总量也可能膨胀：必须显示总 token，批量调整由用户决定，不能暗中淘汰。

详情可以按字段稳定性拆为“稳定档案＋动态状态”，但默认显示范围由用户决定；拆分不等于删字段。

### 7.3 远处也能展开的例子

主角在京城，当前消息讨论远在边关的角色。只要此角色处于本故事有效分支、允许召回且命中明确，即可展开相关档案。其物理位置不阻止激活；状态日期必须保留，不能把旧记录装成实时追踪。

## 8. 自定义模块：前端自由建表，不强制远程建专用表（U + B）

### 8.1 模块定义

模块由稳定 `module_id`、显示名称、schema 版本、字段定义、录入说明、展示模板与注入／召回策略组成。首版字段支持文本、多行文本、数字、布尔、枚举、标签、故事时间、实体引用和来源引用。

内部字段 ID 不随显示名变化；“残响内容”改名成“记忆片段”不应造成数据丢失。字段改类型、删字段和批量迁移需要预览与备份，不能仅改表头就假装数据兼容。

前端新建模块，不必为每一种模块改服务器数据库表结构。远程模式可使用通用记录结构与经验证的 JSON 字段；以后有明确性能需要，再为特定字段建立索引。

### 8.2 【记忆残响】示例

建议字段：发生位置／时间、表层残响内容、触发因素、相关人物／物品、当前解读、状态（未解释／部分解释／已恢复）、来源楼层、关联伏笔、后续兑现来源。

额外可选作者字段：真实含义、未来计划。作者字段默认不进入正文模型和普通召回。一次残响是一条带稳定 ID 的记录；新一轮补充或解释追加版本，不覆盖到失去历史。

自动抽取必须区分“正文明确写出”“角色猜测”“助手推测”。当前角色只知道残响时，不能把作者填写的真相自动转成角色已知。

### 8.3 三种存储模式与两种网络许可

| 模式 | 数据落点 | 迁移与召回边界 |
| --- | --- | --- |
| 远程持久化 | 自托管服务 | 可跨宿主；按策略进入检索 |
| 本机持久化 | 插件本地存储 | 不默认上传；必须能导出／导入 |
| 会话临时 | 当前运行内存 | 关闭可能丢失，界面显著提示 |

“本地存储”与“允许发送给云端副 API”是不同许可。本地模块可以只在前端做关键词命中和注入；远程引擎看不到未上传的数据，不可能替它检索。

允许调用副 API 填写本地表格时，仍可能把选中内容发送给该模型服务。界面必须说明发送范围。严格不离机模式禁止远程副 API、远程 embedding 和远程索引，不能只承诺“不落远程数据库”。

## 9. 前端助手：先提案，再提交（U + B）

助手是工作台工具，不是自动接管记忆库的管理员。首版提供创建模块、建议字段、对选中记录新增／重写／修正、生成摘要和整理对照等动作。

标准流程：选择范围与副 API → 展示本次将发送的数据 → 模型返回结构化修改提案 → schema 与来源校验 → 展示逐字段差异 → 用户确认 → 带 expected revision 提交 → 写审计日志与撤销记录。

助手不能直接编辑原始聊天、执行 SQL／任意脚本、整库扫描后无差别重写。新增事实必须附来源或明确标成用户设定／待核验推测。自动改写用户锁定字段默认禁止。

自动摘要／抽取可以有单独的“可信低风险自动提交”配置，但不会把手动助手的确认要求一并关闭。建表结构迁移、删除、历史回写和覆盖用户编辑始终属于高风险操作。

## 10. 注入规划：内容与位置解耦（U + B）

### 10.1 每类内容返回独立块

每个 `ContextBlock` 至少携带 block ID、内容种类、来源、内容版本、输出角色、语义位置、优先级、预算、是否可压缩和激活原因。服务端不返回只能整体插入的大字符串。

配置继承顺序建议：全局默认 → 模块／类型 → 单条覆盖 → 本轮临时设置。用户可分别移动人物、物品、设定、残响、剧情召回等内容。

### 10.2 位置先按语义表达，再由宿主适配

稳定块建议 `before_history`，动态块建议 `at_depth`，role 可选 user／system，depth 可为 0。文档中的 `user @d0` 表示期望语义，不声称所有 provider 最终都得到完全相同的 messages 数组。

Adapter 必须验证实际输出：role 是否保留、d0 在最新输入前还是后、多个槽的顺序、宿主是否合并 system、text completion 如何映射。无法表示时返回明确能力错误或让用户选择降级，不静默改变含义。

### 10.3 缓存友好，但不承诺命中

稳定档案采用确定性排序，不插入每次变化的时间戳、检索分数和随机 ID。动态召回与当前状态放靠后。稳定记录真正改变时正常更新，不能为了缓存而冻结错误事实。

这只是在结构上减少无关变化。供应商、模型和网关的缓存条件应另行核验；本版不承诺移动位置即可缓存命中，不依赖任何未确认的缓存字段。

### 10.4 预算与最终校验

记忆预算从宿主剩余上下文中计算，预留正文输出与安全余量；不能用“固定能召回 N 条”替代 token 预算。实际 tokenizer 可用时以其计数，否则标估算并保守留余量。

先保留不可压缩的有效重点常驻块，再分配动态状态、概览、事件包与原文扩展。超限给出具体超额块与替代方案。编译后清除重复来源，记录实际被采用的消息顺序。

生成取消、切换聊天或下一轮开始时，清理旧的动态注入槽。副 API 内部请求不得误触发递归召回。

## 11. TT 接入与一次生成的生命周期（B）

### 11.1 生成前

捕获故事／分支／head、宿主 chat 身份、输入内容 hash 和 generation ID。清理旧动态块；同步必要增量。调用 `/v1/context/prepare`，不要求正文 LLM 先决定调用工具。

远程响应回来后，再核对 generation ID、当前聊天和 head。已过时的结果直接丢弃；不能把上一聊天的结果写进当前聊天。合并本地模块，编译注入块，检查预算，再继续 TT 正常正文生成。

是否启用 Query Rewrite、embedding 或 rerank 服务由记忆管线决定。“不先请求正文模型”不等于所有前置过程都不调用模型 API。

### 11.2 生成后

先可靠保存正文版本，再由持久化任务生成叶子、抽取状态、更新事件链接与检索索引。任务失败可重试，不能让摘要失败导致原文丢失。

下一轮到来时，如果上一楼尚未处理，近期原文仍可作为上下文；必须显示派生滞后状态。不要无声使用过期人物状态。等待、继续带近期原文、或手动处理的默认策略列为 E。

### 11.3 故障策略

采用可配置的严格模式与宽松模式。严格模式：重要召回／同步失败时暂停生成，提供重试或一次性跳过。宽松模式：显著提示缺少记忆后继续，动态槽必须清空。错误不得静默伪装为“正常零命中”。

超过超时、用户取消、重写失败、rerank 失败分别记录。降级可以退为词法或向量结果，但不能把不同分数冒充原分数。

## 12. 同步、持久化与可恢复性（B）

### 12.1 增量同步

每个变化有 idempotency key、设备 ID、来源版本和单调本地序列。客户端保存待同步队列，收到服务器持久化确认后才移出队列。重复发送必须只生效一次。

服务器在同一事务中写入正式记录和待派生任务。索引 worker 可重复执行，不产生重复叶子或状态扣减。仅依赖进程内定时器不算可靠任务队列。

并发修改使用 expected revision／乐观锁；发现冲突返回 409 和差异，不以“最后请求覆盖一切”掩盖用户手工修改。

### 12.2 不把重建塞进每轮生成

只索引发生变化的数据；缺失索引通过任务补齐。首轮导入可分批、暂停与恢复。查询需要的正文候选有界拉取；不能每次把全库下载到手机再计算余弦。

当前状态可以通过“状态快照＋快照后的变化”重建。底层变更记录保留，不在每轮请求中从第一楼重新重放上亿字内容。

### 12.3 备份与导出

导出包包含原始消息、版本和分支、叶子、实体／状态变化、模块定义与行、用户策略、来源映射、schema 版本、清单与校验信息。向量索引可选导出，但必须能由正式数据重建。

备份要有独立于运行服务器的副本和恢复演练。代码仓库不是私人聊天数据库；不要把 API key、真实 RP 原文或生产备份提交到代码仓库。

### 12.4 访问与内容安全

前端使用受限的服务凭证，不获得数据库管理员权限。按故事范围授权，HTTPS 与明确的跨域允许列表，错误日志默认脱敏。模型服务 key 优先由服务器保管；本地专用 key 的可见范围与浏览器存储风险要明确。

用户配置模型端点时要校验目标，防止服务端被当作访问任意内网的代理。正文、召回片段、导入文件和模型输出均视为数据，不允许其中的指令修改权限、执行脚本或绕过确认。对本地存储容量、失败与导出做明确提示。

召回缓存除了输入，还应绑定 story／branch／head、memory revision、policy version、模型／索引版本及可见性范围。不能在记忆已纠正后只因输入未变就复用旧结果。

## 13. 逻辑接口草案（B）

这些路径用于明确职责，尚非完整 OpenAPI 或生产 SDK。统一 HTTPS、认证、分页、取消、错误码与 API/schema 版本。

| 接口 | 用途 | 关键契约 |
| --- | --- | --- |
| GET `/v1/capabilities` | 检测后端能力 | 明确哪些检索／模块能力已实现 |
| POST `/v1/sync/batches` | 批量同步消息与变更 | 幂等确认、版本冲突、覆盖状态 |
| POST `/v1/context/prepare` | 生成前记忆准备 | head、输入 hash、预算、独立 blocks、trace |
| POST `/v1/retrieval/search` | 手动检索与诊断 | 精准／混合模式、分页、来源 |
| GET `/v1/sources/{id}` | 回看证据 | 指定 revision、范围与分支权限 |
| POST `/v1/assistant/proposals` | 创建助手修改提案 | 范围受控、不直接改正式数据 |
| POST `/v1/changes/commit` | 确认修改 | expected revision、审计与撤销 |
| POST `/v1/exports` | 创建导出任务 | 快照版本、完整性清单 |

`context/prepare` 返回远程有效记忆，不是直接调用 TT 正文模型。示例请求、响应和模块定义见 `examples/`。

## 14. 前端工作台范围（U + B）

首版导航：概览／同步状态、剧情叶子、实体档案、检索与本轮注入。随后加入自定义模块与助手。不要先追求所有页面齐全而没有可靠存储闭环。

叶子页需要原文与摘要对照、来源跳转、重摘、有效状态和分组修正。实体页需要别名、稳定档案、状态历史、详情／概览／隐藏待召回、字段锁和来源。模块页需要字段编辑、表格／卡片视图、存储位置和发送许可。

检索诊断须展示：本轮原始查询与 Q1～Q5、各分支是否运行、排名与分数来源、被哪个过滤条件排除、rerank 输入类型／是否截断、原文升级原因、最终注入位置与 token。显示“为什么没找到”与“为什么找到”同样重要。

手机界面采用分页或虚拟列表，默认不加载全库详情；长文本按需打开。UI 可显示全部档案入口，不意味着每轮都把全部档案发给正文模型。

## 15. 从柏宝书渐进迁移（B）

### 15.1 影子模式

保留现有柏宝书的工作方式。新桥接器只读公开 API／合法导出的聊天，写入新后端并提供独立搜索，不注入正文、不覆盖柏宝书数据。读取 API 的覆盖信息，导入报告明确缺失来源与无效版本。[B04]

公开 API 的 getFloor 返回清洗文本，不保证完整保留原消息。桥接导入要标明 raw／cleaned／summary_only；真正的原始档案优先从宿主原始导出取得，不把清洗文本冒充未经改动的原文。

先验证能导出、恢复、按原句查到证据，再比较新旧召回。不要先在用户唯一存档上运行自动改写。

### 15.2 单一注入责任

每类内容只能有一个主动注入者。迁移时建立责任矩阵：历史摘要可以暂由柏宝书负责，剧情召回由新系统负责；实体和自定义模块在各自验收后切换。不能同时让两套插件对同一类记忆重复注入或相互覆盖。

关闭旧检索注入前先保留备份和可回退开关；原插件不卸载也能逐项移交。公开 API 只读，因此修改工作台数据默认只写新系统，不伪装成已回写柏宝书。

### 15.3 不以大改旧插件作为唯一道路

优先新建薄桥接器和独立服务，再按实际需要复用经授权的界面／逻辑。若要复制或发布已有代码，先完成许可与归属核查；不能因为仓库公开就默认可任意再许可。本版不作法律结论。

## 16. 规模边界与长剧情占位（B + D）

远程引擎的容量与 TT 当前活动聊天的容量分别测试。新系统不要求全库进前端，但不能仅靠外接数据库就消除 TT 完整聊天加载／保存的开销。[T02]

保留故事 ID 跨多个宿主聊天的映射，作为必要时分篇的技术出口；这不是要求用户现在拆聊天，也不是假装拆篇体验完全等价。真正单一无限滚动界面需要宿主支持或单独改造。

当前只预留四类上下文来源：当前有效状态、未解决的计划／伏笔、历史骨架、按需证据。骨架怎样生成、多久更新、旧总结是否常驻、是否建立层级目录，均为 D。

保护性约束：旧总结可以退出本轮提示词，不因此自动删除存储中的叶子、原文和因果链接。检索不保证召回所有重要细节，因此“全靠一次向量搜索”的连贯性方案不能未经评估就定为最终方案。

## 17. 版本与验收纪律（B）

实现按 `02-roadmap.md` 的任务顺序推进。每个任务只交付一个可演示增量，必须附测试结果、已知限制、回退方式和受影响文档。

功能状态统一为：planned、in_progress、implemented_unverified、verified、blocked。编译通过不等于手机联调通过；样本召回正确不等于亿字性能通过；下载了依赖不等于后端能力已实现。

任何改变数据格式、激活优先级、用户字段或注入语义的修改，先记录决策与迁移方案。文档与代码在同一变更中更新；旧决策标为 superseded，而不是删掉历史。

### 本版一句话基线

**先拥有可恢复的故事档案；保留每楼叶子，把跨楼事件、实体激活与注入位置独立出来；TT 只当首个前端，MCP 只当可选入口。**
