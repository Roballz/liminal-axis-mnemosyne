# 文档、GitHub 与编码助手的协作方式

v0.1 · 核验日期 2026-09-17

## 1. 推荐存放位置

把 Markdown 文档和未来代码放在同一个私有 GitHub 仓库，作为唯一的工程基准。Markdown 是普通文本，适合逐行查看修改、保留历史和交给编码助手；Word 仅作为方便阅读的导出副本，避免两边独立编辑后冲突。

真实 RP 数据、模型密钥和生产备份不要进这个仓库。另建受控数据存储和备份位置。是否公开项目、叫什么名字、谁有权限，要由用户明确决定。

本次只提供可上传的本地文档包，没有创建远程仓库，也没有提交 GitHub。

## 2. ChatGPT 项目怎么用

当前官方 Projects 文档支持添加文件和保存回答为项目来源。[O01] 可以把主文档和未决事项的当前快照放到 RP记忆系统 项目，方便继续讨论。版本号要清楚；同名重新上传不应被当成自动更新了唯一文件。

连接 GitHub 后，ChatGPT 可按授权读取仓库中的代码与文档；可用入口受账号和产品界面影响。[O02] 本次会话实际使用了 GitHub 读取工具。以后讨论时指定仓库、分支和文件路径，比假设模型会自动记住所有聊天可靠。

项目附件是讨论上下文，不应被当作与仓库实时双向同步的工作目录。重要决定最终写回仓库；只有更新附件而没更新仓库，Codex 不会因此自动得到新的工程规格。

## 3. Chat 与 Codex 能否共用文档

可以通过读取同一个仓库／文件夹共用工程文档，但不应假设“Chat 里的附件已经自动变成 Codex 工作文件”。当前官方说明仍区分 ChatGPT 和 Codex 的历史；Codex 可操作本地文件夹和仓库。[O03]

可靠做法：给 Codex 打开同一仓库，指定 docs/01-architecture.md 和本次 task。AGENTS.md 用于约定开工前的读取顺序与工程边界；官方文档说明 Codex 会读取相应 AGENTS.md。[O04]

工具入口会变化，不在本文件硬编码某个客户端菜单。GitHub 写权限与读权限分别核验；能读取一个仓库不等于能创建仓库或推送更改。当前未发起任何写操作。

## 4. 一次完整工作循环

在 Chat 讨论一个问题并 review 上一 task → Chat／用户创建或确认下一张 task → Codex 在任务分支只实现这一张 task → 运行测试与目标平台验证 → Codex 写回实施回报但不创建下一张正式 task → Chat 读取 commit／证据做 review → 再决定下一张 task。

Issue 是待做事项；task 是具体工作单；分支是隔离改动；commit 是一次可追踪保存；PR 是合并前检查修改的入口。一个人开发也能用这套最小流程，不必引入复杂项目管理工具。

## 5. 给 Codex 的首轮任务文本

> 请以当前仓库 README.md、AGENTS.md、docs/01-architecture.md 和 docs/03-decisions-and-open-questions.md 为准，只执行 tasks/T-00-baseline-and-probe.md。先报告你实际读到的版本和缺失环境。不要实现全部系统，不要使用真实 RP 存档，不要修改现用柏宝书。无法运行的检查必须标未验证。输出可复现的能力清单和下一项任务所需证据。

## 6. 更新文档的规则

需求改变先改需求与决策；实现细节改变同步代码和相关章节；接口改变附迁移；已知限制写进 task 与 release 说明。CHANGELOG 记录变动，未决项关闭必须附测试或用户决定。

主文档不要持续无上限膨胀：稳定概念留主文档，详细实验放 evals，已完成工作记录放 tasks。每次任务只读取必要章节。

来源链接和核验说明见 docs/05-source-review.md。


## 7. 阶段导读与交接文档

仓库承担 Chat 与 Codex 的共享记忆，不另建无限增长的交流日志。

- `AGENTS.md`：只放长期稳定的全局工作约束与交接规则。
- `stages/S-XX-*.md`：由 Chat 在每阶段开工前维护，给用户和 Codex 同时阅读；包含阶段目标、任务一句话地图、阶段完成线、已确认输入、待定方案、当前阻塞与需要用户提供的资料。
- `tasks/T-XX-*.md`：单个可执行增量。Codex 在任务结束时把“实施回报／交接”写回同一文件，不另建重复报告。
- `docs/03-decisions-and-open-questions.md`：跨任务且会影响架构／语义的正式决定与开放问题。
- `evals/`：实验方法、测试集和详细测试证据；大段运行输出不要塞进阶段导读。
- `notes/`：环境基线、一次性调查和不适合作为长期规范的事实记录。

阶段导读由 Chat 负责“为什么做、做到哪里、还要决定什么”；task 的规划与验收边界也由 Chat／用户负责，Codex 负责“具体实现与证据”。Codex 默认只在收尾报告下一任务依赖／建议验证点，不提前建立下一张正式 task。只有 Chat／用户明确要求时，Codex 才能在当前 task 完成后写 `proposal` 草案，等待 review。阶段结束后由 Chat 读取所有 task 实施回报做阶段 review，再决定下一阶段导读。

## 8. Codex 实施回报的最小字段

每个 task 收尾至少记录：

1. 基线 commit／工作分支／最终 commit 或 PR；
2. 实际修改的文件与行为；
3. 实际运行环境、命令和测试结果；
4. 可复现证据（trace、截图、fixture、日志位置等，不提交隐私数据）；
5. 实现过程中观察到的真实宿主／API／数据格式事实；
6. 与原任务卡不同的地方及原因；
7. 未验证项、失败项、阻塞和技术债；
8. schema／接口／数据迁移／兼容性影响；
9. 回退方法；
10. 下一任务所需前提；
11. 必须由 Chat／用户讨论决定的问题。

“观察事实”和“设计选择”必须分栏。可逆的局部实现选择可由 Codex完成并记录；会改变产品语义、架构、数据模型或不可逆迁移的选择，应停在问题状态等待方案确认。

## 9. Chat 端项目提示词与仓库各放什么

两边都要写，但职责不同。Chat 项目提示词只保留角色分工和行为规则，例如“Chat 负责方案／阶段 review，Codex 负责实现／测试”“阶段开工先输出阶段导读”；具体阶段目标、版本、输入资料和决定全部写仓库。

原因：提示词只约束 Chat，本身不是 Codex 可审计的工程历史；仓库才是两边都能读取、能 diff、能追踪版本的正式交接面。
