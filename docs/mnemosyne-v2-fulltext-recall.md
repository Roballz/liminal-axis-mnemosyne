# Mnemosyne 重构方案 · 手机端历史正文检索

2026-11-24。设计已确定首选和降级顺序，正式实现与 Android TT 真机验收待做。目标是在一两千万字的历史正文中，找回摘要省略的台词、物品、称呼和当时的问答，同时保留原场景。分支已有的[剧情时间树](mnemosyne-v2-time-tree.md)提供剧情日期和来源定位。

## 选型顺序

保留摘要 Embedding、摘要 BM25 及现有融合和重排。新增一条独立的本地正文召回路线。一次启用一种正文索引，三种组合共用同一套范围过滤、原文核对、场景选取和注入规则。

| 优先级 | 与现有摘要召回搭配的方案 | 采用条件 |
| --- | --- | --- |
| 1 · 首选 | 插件自带启用 FTS5 的 SQLite WASM，由一个专用 Worker 持有 OPFS 持久连接。正文用 trigram，短词另建索引。 | 先在官方 TT 安装版验证资源加载、重启恢复、长档查询和增量写入。通过即采用，随插件发布。 |
| 2 · 兼容降级 | Worker＋IndexedDB 分段倒排。先查字组所在的索引段，再取候选楼；沿用同一短词规则。 | 当目标 WebView 的 WASM、OPFS、持久化或资源占用存在可复现、定位后仍无法解决的问题时启用。普通查询未命中、一次临时写失败都无需换引擎。 |
| 3 · TT 专用备选 | 仅在明确选择 TT 原生方案时，接 TriviumDB 文本和关键词索引，复用通用层回读正文。 | 可用于 TT 专用部署或真机对照。优先级 2 是默认降级终点。 |

## 整楼正文与场景归属

核心库保留玩家与角色的完整原始楼层。按当前故事、分支和截止位置选取有效正文版本，已归档且允许召回的旧楼即使没有 L0 也可独立建索引。每个版本可关联楼层顺序、说话方、正文指纹和可用的 L0 引用。共享前缀按来源版本复用，显示楼号、SQLite rowid 和 TT NodeId 仅作映射。

**一楼 2,000～4,000 字可整体建索引。** 索引的“分段”是把一批楼层的检索数据一起落盘；500 字只是前期合成实验的段长。默认保留自然段和问答边界。候选入选后，回读少量整楼，定位原句、提取所需上下文。搜索投影可以统一全半角、标点和空白，排除思考块、状态栏等按配置清洗的内容。保留原始偏移映射或在原文重新定位，避免跨楼、跨不相干段落拼出一次连续命中。

起止标签和内部原始文本随楼层完整保存。用户现用格式示意如下：

```xml
<globalTime>年月日时 星期 天气 地点 节假日名</globalTime>
（整楼正文，可含多个自然段、转场、回忆或录屏）
<endTime>年月日时</endTime>
```

- 在清洗正文前提取首尾标签。开头按可可靠识别的内容派生开始时间、星期、天气、地点、节假日名，末尾派生结束时间。沿用旧档 `<bbs_start>`、`<bbs_end>` 支持，并保留已知字段的来源。对缺字段、多词地名、架空历法、自由文本或两套标签冲突的情况，保留原值与可确定的部分，避免按空格硬拆、补造日期，或将不同协议的首尾随意配对。[旧版时间解析](../src/memory/timeTag.ts)
- 日期范围有可靠依据时可作过滤条件。开场天气、地点、节假日可以参与检索，并随命中标明“本楼开始时”。换场后优先回取命中前最近的明确转场。只有楼首和楼尾时，给出楼层时间范围；回忆发生时、屏幕内事件发生时、角色后来转述时分别依原文判断。
- 跨日楼保留一个完整来源。已有时间树能定位到具体片段时复用其范围；时间树仅有粗范围时，仍可回到原楼。高层合并或重写摘要不触发未变正文的重建。

## 从长输入找回原话

1. **提取线索。** 从最新玩家输入全文以及各条改写 Q 分别取线索。对“上次你问”“当时说过”等附近的原句优先，并从整条输入选较少见、分布在不同句段的连续字组作补充。嵌套引号、漏引号、Q 被改写成宽泛场景时仍能检索。排除本轮输入、当前已完整可见的正文、重生成时待替换的回复和其他不可发送来源。
2. **长短词分开。** 三字以上的连续线索先走 trigram。完整短语用于找原话；记差一两字时，用若干稀有字组找候选，再回原文检查顺序、连续长度、距离和附近的角色或动作。两字人名、地名、物品和称呼（如合成例“苏禾”“铜钥”）走独立短词表，保存“词 → 来源版本”。已确认别名可扩展查询，同时保留原称呼、适用故事和有据可查的范围。称谓猜测、人物被提到或在场分别处理。
3. **补足词表覆盖。** 第一版从已有名称和确认别名登记短词。只有一个未登记两字词时，可先使用摘要或同一输入的其他线索召回，再核对原文；检索详情标明覆盖范围。若实测漏召主要来自任意两字词，评估增加通用双字倒排，只记出现过该词的不同来源，再回正文验词。按空间和写入成本决定是否启用，避免每次搜索临时扫描全库。
4. **选场景。** 在当前分支可见范围内分别保留较早的逐字命中和与本轮场景最相符的候选，再截取最终名额。若引擎只给相关性前 K，需另按有效楼序取早期候选或按时间范围分页。将同一场戏相邻楼归组，用人物、动作、问答区分原始现场与后来复述。最早出现只是一条线索。查询同时涉及承诺和兑现时，可各留一段，按剧情顺序回传。
5. **合并与注入。** 对已核实、足够独特且符合本轮回忆线索的整句，在总预算内保留原文证据，避免宽泛的 rerank 再次将它淘汰。近似或歧义命中参与普通排序。按来源版本和命中范围与摘要、已有全文和相邻楼去重，先带相关场景交代、原句和实际应答；回答跨楼时只取需要的相邻内容。确需整楼且预算足够时再展开。详情可显示命中短语、楼层、匹配方式、覆盖进度和取舍原因。

## 两种可移植实现

**SQLite WASM。** 插件内发布对应的 JS、Worker 与 WASM 资源，实际创建 FTS5 表验证构建选项。首试 OPFS 的 `opfs-sahpool`，让一个 Worker 管理连接。以应用来源版本映射内部 rowid。FTS5 使用 trigram 和支持短语位置的配置；可用支持更新/删除的无正文 FTS 表保存规范化后的检索信息，展示时按版本回核心库。短词使用普通索引表，按词和来源去重。提交一批变更时事务性写入检索项、短词映射和进度。FTS5 在后续写入时可能合并小段，须测合并期间的延迟及空间峰值。[FTS5 分词、表配置和合并](https://www.sqlite.org/fts5.html) · [WASM 的 OPFS 存储选项](https://sqlite.org/wasm/doc/trunk/persistence.md)

**Worker＋IndexedDB。** 用按故事和来源版本分页的字组目录查找相关段，段内保存“字组 → 楼层版本”的紧凑列表，候选楼再按需读正文。较早已封存的段保持只读，新增和替换版本进入活跃段。目录也按词和小块更新。写入新段后用事务切换目录与进度，避免每改一楼就序列化整份目录或全部文档。后台有界合并，读取者只使用已发布的版本；中断后从上一个已提交批次续建。

**两者共用的更新规则。** 新增和编辑只处理变化来源；切 swipe、继承或切分支、删除、恢复核心包后，以当前有效版本重新约束命中。查询范围在取候选前限定，并在异步返回或注入前复核。后台合并、恢复和清理要保留其他分支仍引用的版本。索引是可重建缓存，排除在核心包之外。首次构建按页读取，普通发消息只查已建范围，不等待整档重建，不把整段聊天复制到 UI 线程或一次性发给 Worker。索引尚未覆盖、索引失效和已覆盖但无命中要能区分；摘要召回可独立工作。

## TT 原生路线的接口和限制

以下按 TauriTavern `85dc990`、TriviumDB `0.8.8` 核对，仅作为 TT 适配器的实现依据。

| 步骤 | 已有接口及用途 |
| --- | --- |
| 打开与映射 | `window.__TAURITAVERN__.api.db.open(namespace, options)`。按明确维度创建专用命名空间，以 `insert(vector, payload)` 或 `batchInsert(vectors, payloads)` 获得 NodeId，维护到正文版本的映射。文本登记需要已存在的节点；原型要验证节点创建所需向量占位和空间。 |
| 建索引 | `indexText(id, text)` 注册正文。0.8.8 对连续中文使用双字组，BM25 能用两字线索。可用 `indexKeyword(id, keyword)` 显式登记专名和已确认别名。词频索引没有正文位置，连续短语仍需回读核对。 |
| 批量完成与查询 | 批量登记后调用 `buildTextIndex()`，TT 会编译并执行一次 flush。使用 `search(null, {queryText, topK})` 发起纯文本检索，命中返回 id、score、payload。`searchAdvanced` 可辅助观察阶段与耗时。 |
| 重开与恢复 | 手工文本登记不进入 WAL。0.8.8 保存时会写出该命名空间完整的文本索引，已有索引在 TT 重开时会被加载。冷启动、批量保存、编辑后旧词失效均需验证。若采用独立小库来限制写放大，还需验证跨库查询和结果合并成本。 |

以上接口不要求改 TT 或开放任意 SQLite SQL。原生分词、关键词和 QuIVer 向量检索是不同能力；本方案针对正文词法检索，摘要向量后端另行评估。[TT Database API](https://github.com/Darkatse/TauriTavern/blob/85dc99089e3fcc9d3a0aafc085564bd642895261/docs/API/Database.md) · [TT 调用实现](https://github.com/Darkatse/TauriTavern/blob/85dc99089e3fcc9d3a0aafc085564bd642895261/src-tauri/crates/tt-adapter-triviumdb/src/operations.rs) · [TriviumDB 0.8.8 分词与存盘](https://github.com/Astrmira/TriviumDB/blob/v0.8.8/src/index/text.rs)

## 落地顺序与验收

| 顺序 | 交付与判定 |
| --- | --- |
| 1. 真机验证首选 | 在独立测试索引中验证 TT 安装版加载插件自带的 WASM、FTS5 建表、OPFS 落盘、关闭重开、增量编辑和删除。验证失败先定位资源路径、WebView 能力、配额或持久化原因，一天作为初次验证的时间预算。记录无法解决的问题后才转 IndexedDB。 |
| 2. 固定检索样本 | 用合成的 2,000～4,000 字整楼与独立预期楼号验证。覆盖长输入里的嵌套引文、标点差异、错一字、两字专名、未登记词、别名歧义、只有玩家楼有原话、没有 L0、同句多次复述、原始问答跨楼；检查目标在候选、选中和最终注入三个阶段的去向。 |
| 3. 验证来源与场景 | 覆盖首尾标签、缺损或冲突标签、多词地点、楼内转场、跨日、内嵌录屏及转述。同段重复引用仅注入一次。编辑、切 swipe、切分支、删除、恢复后，检查命中对应的正文版本与当时场景。 |
| 4. 验证长档与交互 | 用 1,000 万和 2,000 万字整楼语料分别测首次建库、重启首查、热查（常见词与罕见引文）、追加与编辑一楼、后台合并与续建。记录索引体积、临时空间、峰值内存、每查读取字节和候选数、查询延迟及聊天滚动长帧。与关闭正文路线的同机基线对照；单楼变化应有界写入，正常发消息期间无全库读写或重复刷新。 |

前期量级参考用的是 4 万段、每段 500 字的合成文本。桌面 JS Worker＋模拟 IndexedDB 验证了段目录能将三条罕见台词各自的读取量从约 2.8～3.0 MB 降至约 84～89 KB。同批语料的桌面原生 SQLite FTS5 位置索引文件约 92.2 MB。两次实验都找回了每条台词的三次出现。两者的存储统计口径不同。这些结果只用于选择真机测试项，整楼语料、常见词、Android I/O 和交互延迟仍待验证。
