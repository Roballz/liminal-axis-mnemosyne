# 旧核心包与宿主摘要的来源恢复

## 为什么会显示“摘要基线缺失”

核心包不包含宿主聊天文件。恢复较早的核心包后，宿主仍可能保留较晚生成的摘要，以及指向当时生成快照的来源标记。继承祖先档案可以成功，但随后归档这些摘要时，旧包没有对应快照。旧实现先提交摘要，再在状态投影时失败，因此界面的正文/摘要计数可能仍为 0；这不是数据库为空的证据。

这个引用接入路径在 1.3.15 已存在，不能仅根据错误把它归因于 1.4.0 的正文保存策略。当前修复由合成宿主、fake IndexedDB 和真实桥接调用验证，尚未声称完成 Android/TT 现场验收。

## 修复与保存边界

- 同步时核对宿主已匹配摘要的生成基线。缺失的基线不再变成可用来源，也不伪造历史快照
- 摘要正文、原 `basis`、`inputRefs`、`coverage`、摘要 ID 和家族 ID 保留，只增加版本化 `sourceRecovery` 声明，记录缺失原因和本次观察快照
- 当前分支此前已提交的坏摘要及未选中修订，仅当宿主摘要 ID、基线、输入引用和覆盖范围与当前宿主来源声明一致时补上该声明。父档案及其他分支不改写
- 无效摘要处于待人工核对状态；其高层依赖也不能自动进入有效召回、事件生成或继承。既有审核回执不能把此声明变成有效生成证明
- 对未声明的引用缺失、跨故事引用、错误的现有来源身份、非法声明或未知声明版本，导出和恢复继续严格拒绝
- 来源恢复只读取当前分支摘要元数据和其指向的快照，不扫描全部历史正文，不调用摘要模型，不删除宿主摘要或旧修订

## 人工处理

归档成功后，先查看待核对摘要。“核对并保留 N 条现有摘要”收集当前分支待审核、可与宿主身份、正文、回复版本及摘要精确对应的公开、启用 L0。缺失旧基线和普通来源待审核的 L0 可以进入同一批次；L0 在生成时引用过其他摘要，也不会仅因此被排除。已有效摘要不重复纳入。高层摘要、映射不明、停用或来源不一致的条目不混进批次，页面直接显示具体排除原因及数量，无需先展开逐条卡片。

核对每条摘要所在楼层及此前的当前正文后，点击批量按钮，阅读数量与范围，再点“已核对，保留这些摘要”。也可展开“逐条查看与处理”，点“核对并保留此摘要”，或用“核对并手动确认”修改文字。确认前取消不写入；聊天切换、正文或摘要版本改变时不沿用旧的确认目标。保存失败会整批回滚；如果确认已保存而随后刷新失败，错误会明确说明已经保存的数量，不能把它当成未提交而重复操作。

可以保留原文不改。保存明确表示确认摘要适用于这段当前正文，另存人工确认版本；这不表示原生成证据已经找回。确认框明确说明：本次以你核对的当前正文为依据；旧生成时引用的摘要和来源保留在旧版本中。旧摘要、原 ID、原基线、输入引用、覆盖范围、摘要依赖及缺失来源声明继续保留。新人工版本共享本次固定快照，并用各摘要锚点界定到该楼为止的前缀；它不再依赖旧生成时引用的摘要，也不把长前缀重复写入每条摘要。批次只发布一次选择与分支版本，不逐条重放宿主或重新同步；宿主摘要与来源侧标记不改，不调用摘要模型。

之后编辑该楼及此前的真实正文，人工确认版本仍会重新进入待核对状态。只修改旧生成依赖的其他摘要，不会否定这次独立的人工正文判断；只修改自身标签会保留已选人工来源。上级摘要和事件概要按其依赖另行审核，不自动一起放行。数据库仍为 DB3、核心包仍为 v13，不需要重新继承或导入。
也可以明确选择重新生成摘要，此操作才会进入现有的模型调用确认流程。

## 核心包 v13

v13 允许严格定义的来源恢复声明：`{ version: 1, reason: 'missing_basis', snapshot: <观察快照 ID> }`。原基线必须确实不在包中，观察快照必须存在且属于同一故事；原来源 ID 按未解析历史证据保存，已有的消息和版本仍检查故事及身份一致性。声明不会豁免正文、事件、依赖、当前 Head 或其他引用检查。

新导出和原生核心备份使用 v13，v1–12 仍可导入。数据库仍为版本 3，不新增存储。旧版插件不能导入 v13；升级前的旧核心包继续保留，勿为降级删除当前数据。

## 保守停止情形

如果失败继承后又编辑或切换了摘要，某个未选中的坏修订可能不再与当前宿主证据相符。修复不会凭相同文本、楼层或故事猜配这些历史记录，也不会自动标记所有损坏数据。此时完整导出仍可能明确报告缺失引用。

应保留当前宿主聊天、当前库和已有核心包，停止反复导入/继承；先只读比对能包含该生成基线的较新核心包及对应宿主来源记录，再确定有证据的定向修复。没有对应记录时，需要单独审查并明确授权如何保存这些无法匹配的历史声明；不能靠缩短继承前缀、删除摘要或关闭校验来恢复。
