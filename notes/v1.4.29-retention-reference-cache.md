# v1.4.29：历史引用计数与正文回收

基线：`3d15204150047662bed1fc4e39a5d5525a041ca3`，分支 `work/daily-memory-mvp-baibai`。

按用户指定顺序，F04、F12–F13、F18–F24 已在 v1.4.27 完成，F25–F27、S01–S07 已在 v1.4.28 完成。本批单独处理最后的 **F11**。

## 剩余问题与本批改动

v1.4.26 已让具有明确存活证明的追加跳过历史回收。但用户消息后追加 AI 回复时，旧用户 head 通常没有永久引用，仍需扫描九类历史证据才能决定删除哪些快照。历史摘要正文和嵌套引用随每次扫描被反复读取。

本批为这九类证据建立每个 Library 连接内、按 story 分组的精确引用计数。缓存只保存快照 ID、正文修订 ID 及其计数，不保存历史文本或完整记录。第一次需要回收时完整扫描；后续正常摘要、审核、事件、表格写入按旧记录与新记录的引用差值维护计数。

- 主库物理版本从 **v4 升到 v5**，新增内部 `retention_control` store。相关写事务同时锁定并更新提交标记，其他连接即使没有修改 branch epoch，也会使旧缓存失效。
- 每条记录按旧回收器的递归规则收集 `basis`、`snapshot`，以及同时具有字符串 `message` 和 `revision` 的来源引用。包括 receipt output、表格值和嵌套来源恢复记录；同一记录内重复出现只贡献一次，多条记录共享同一引用则分别计数。
- put/delete 先排队读取旧记录，再立即排队原生写入，不在中间 await。连续对同一 key 执行 put、put、delete、add 保留 IndexedDB 原有顺序。新引用在调用时提取，不受调用方随后修改对象影响。
- 冷扫描记录每个 store 的读取边界，已经包含的写入不重复计数，扫描之后的写入按差值补上。事务中可读取暂定结果；连接缓存只在原生事务成功提交之后发布，回滚不发布计数或提交标记。
- 首次使用、其他连接提交、重新打开库或显式完整维护检查会重新扫描。有效缓存下的日常追加与新摘要写入不会反复读取历史证据。

只替换原回收器的九类证据收集步骤。分支 head/fork/legacy、所有分支的当前正文、role repair 证明，以及快照、清单块、旧正文和来源描述符的删除条件继续执行原逻辑。未通过遗留无引用快照或放宽历史保留规则换取性能。

## 针对性验证

使用 80 条正文、40 条当前摘要，额外添加 0、500、2000 条未选择历史摘要修订。直接统计原生 IndexedDB story 索引读取，避免仅统计包装方法而漏掉实际 IO。

| 连续操作 | 读取历史摘要修订行数 | 九类证据扫描次数 |
| --- | --- | --- |
| 冷缓存追加用户消息 | 0 | 0；明确存活证明允许跳过 |
| 随后追加 AI 回复 | 40 / 540 / 2040 | 各 9 次，建立完整引用证明 |
| 新增摘要 → 用户消息 → AI 回复 | 每步 0 | 每步 0 |
| 再新增摘要 → 用户消息 → AI 回复 | 每步 0 | 每步 0 |

另以两份相同档案作差分：一份使用新缓存，另一份每次都执行独立抄录的原始完整证据扫描并强制回收。14 步追加、摘要创建/修改/移除、正文编辑、swipe、删楼和分叉后，逐步比较所有业务 store 的完整记录，最后比较导出包 data，结果一致。额外强制完整回收不会留下新的可删除记录。

协议回归覆盖全部九类证据、跨 story、共享引用最后一次删除、同 key 连续排队写入、调用后对象变更、冷扫描中交错写入、强制刷新、冷/热事务回滚、原生写入失败，以及其他连接在 branch epoch 不变时的新增、替换和删除。物理升级保留旧记录；被阻塞并已返回失败的升级请求在旧连接关闭后会撤销，不再偷偷完成升级。显式重试可以正常完成。

上述计数与比较来自合成数据及 fake IndexedDB，不是 TT 或手机的实测耗时。有效缓存仍需遍历引用 ID 和现有回收元数据，未宣称整个回收过程是常数时间。

## 数据与协议边界

核心导出包继续为 **v15**。内部控制 store 不加入 `STORES` 或导出包，导出恢复不携带旧连接的缓存证明；恢复到新库后重新建立引用计数。现有 v1–v15 包兼容路径保留。

主库 v5 阻止旧 v4 程序继续作为写入方打开同一个库。所有生产主库写入继续通过 Library 事务 API；直接绕过 API 使用原生 IndexedDB 写入不在该缓存协议内。内部提交标记采用安全整数，达到上限会拒绝证据写事务，不会复用旧值。
