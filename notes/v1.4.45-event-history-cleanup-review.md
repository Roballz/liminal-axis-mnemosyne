# v1.4.45 事件链历史清理修复

## 范围与根因

- 基线：`work/daily-memory-mvp-baibai`，`ba4ee198edfb5832ea6757d445beee9f3f2d8e4d`，v1.4.44。
- 用户报告：历史清理后事件关联 77→45，251、255 楼存在但中间 253 楼关联消失，摘要本体仍在；概要及可能的关键词消失。
- 合成反例：仅中间摘要存在旧修订，事件已基于当前摘要生成；旧实现仍将 3 条关联删成 2 条，并清空概要、最新进展和追加进展。纯标签等价修订也能触发。
- 原因：清理把未选中旧修订交给实际改文的失效处理，后者按摘要家族扩散，把当前引用也加入失效集合。
- 关键词在反例中始终保留；用户实际关键词现象尚未通过私人数据核实。

## 实现

1. 历史清理使用专门的事件引用整理，保留事件文字和实际来源，不再模拟一次正文/摘要改写。
2. 成员按明确摘要家族重绑当前版本，原操作 ID、epoch、snapshot、cutoff、人工锁定、增删状态全部保留。
3. 概要及进展只重绑严格等价来源；非等价旧来源保留为真实依赖，原待审核状态不被自动批准或清空。
4. 实际改文的既有失效处理继续执行，但排除当前及等价版本；旧人工解除记录不再提升 epoch。
5. 等价判断移到无环依赖的小模块，canonical 保留原导出接口；核心包仍为 v18，无数据库格式升级。

生产源码约 85 行新增、13 行删除；新增 180 行、5 项回归。包括安装文件、版本和文档更新。

## 性能与数据边界

- 事件整理位于显式清理 Worker 的既有一致快照计划；按分支索引读取，按摘要 ID 缓存读取及等价判断。
- 不增加页面打开、刷新或普通追加时的全库扫描、定时器、模型请求和正文读取。沿用原子提交、并发写入检查及完成后缓存失效。
- 引用仍需要的旧摘要会保留，不能为了进一步压缩而删除当前事件的来源证明。
- 所有运行验证均为 Node、fake IndexedDB 和已有 Worker/Vue 探针；未读取用户真实核心包，未做 Android/原生 TT 帧率实测。状态为 implemented_unverified，等待用户实际档案验收。
- 升级不自动恢复已物理删除的事件内容。恢复需清理前核心包/备份或可核实的独立分支副本；摘要还在不代表原事件归属和原概要仍可重建。
- 回退代码不会回滚已经执行的数据清理。需要旧行为排查时应使用独立备份副本；不要再次用 v1.4.44 清理真实活动库。
