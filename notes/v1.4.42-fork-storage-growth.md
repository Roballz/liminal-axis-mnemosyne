## 现状与证据

用户首次分叉 176→267 MiB：memories 19950→36385（+16435），source_messages 2624→2635（+11）。这次增长发生在删除前，不能归因于删除未回收。统计中的 memories 是摘要身份，包含当前及历史依赖身份，不等于页面当前摘要数；同一身份的多次修订通常应归入 memory_revisions，而不是不断创建新身份。

forkBranch 新建分支、绑定、快照、选择视图和消息映射；正文沿用父引用。inheritForkMemory 新建子分支摘要身份及修订，映射高层依赖和审核证据；inheritForkEvents 本地化事件；inheritTableHistory 遍历截止点可用的表格历史，递归复制其中旧摘要来源。当前实现是正文共享、摘要大字段共享编码，摘要身份/依赖/表历史仍按分支复制，并非完整写时复制。因此没有新聊天也会新增这些记录。

旧实现按源修订 ID 复用，不能识别旧错误继承留下的不同 ID、相同生成证据。表格历史再次触及它们时会继续复制。受控复现：父档案当前只有两条摘要，但历史表引用 128 组完全相同的叶子/高层身份，另有一份声明不同的历史证据。基线代码首次分叉新增 259 条；新代码新增 3 条，消息身份不增加。导出/恢复后再次分叉仍为 3 条。基线反例确实执行并失败于 259 != 3。不能由该实验认定真实 +16435 全部属于同一种重复；无用户逐行档案无法给出真实各路径占比。+11 消息身份也不是 forkBranch 本身直接创建，需实际同步证据才能归因。

用户 267→312 MiB 对照：总增 46,792,474 bytes，共享块增 47,379,466 bytes / 33,523 块，其他表净减少 586,992 bytes。旧删除按 branch/owner 删除，memory_payloads 无这些字段，所以没有回收。合成紧凑库已复现子分支专属依赖块删除档案后遗留；这是独立于首次分叉的第二个问题。

## 修改

- fork-evidence / fork-memory：先映射依赖，再对完整生成证据建立事务内哈希索引；哈希仅路由，命中后完整比较。不以文字或 hostId 单独判同。只复用子分支内完全一致的表格历史证据；当前选择/已复制审核身份不强行合并，父记录不改写。按源 ID 缓存复制 Promise，顺序处理依赖，检测循环及缺失，避免重复展开/竞态创建。
- shared-garbage / archive-deletion：在用户明确删除档案时，从所有保留的物理摘要、审核及历史选择视图标记共享块与选择节点，只回收不可达项，包含之前删除留下的孤块。沿物理引用遍历，不能用展开后的逻辑记录作为共享块根。缺失引用停止；仍有子分支的父档案继续禁止删除。
- db / retention-roots：删除共享块前排空旧证据异步读取；删除与回收仍在同一事务，失败整体撤销。
- 删除过滤使用 Set，避免删除数与全表行数相乘的 includes 扫描。未增加后台扫描、UI 刷新、普通同步全表扫描或自动 GC。预览和完整校验仍有全包开销；本次没有声称解决恢复三四分钟的全部性能原因。

没有包格式迁移，回退可继续读取。更新不自动改写现存档案，也不追溯合并父档案既有历史身份；新分叉不再复制可证明完全相同的表历史证据。已存在的无引用物理块可由现有显式核心库整理重建去除；无需为回收而删除有效档案。不同生成证据的合法历史仍保留，故不能承诺后续分叉固定零增长。
