# 日常导入慢：紧凑记录提案回审与大档案边界

日期：2026-09-22。审核提案：`0fa36e6f56222085208d1ff832b9c7c542a8108e`。原提案：`notes/manual-search-demo-storage-compaction-proposal.md`。

状态：**有条件认可紧凑记录方向；兼容条件须补齐。不是实现验收，不宣称千万字可用，也不自动授权升级用户现有库或切换 provider。** 本轮仅源码/既有证据审阅及公开技术资料核对，没有执行代码、计量、TT/手机实验，没有修改实现或创建新任务卡。

## 1. 结论

- 当前首先是 Mnemosyne 自身的记录粒度与目录放大问题，不能凭这份数据认定 Rust、TT 或 TriviumDB 本身写正文很慢。
- 小型不可变记录整体编码、长正文单独分块，符合现有 Story/Branch/Revision/Head 及可靠恢复的目标。不可变并不要求每一个 JSON 字段都成为持久页。
- 这是持久编码/根格式的兼容升级，不是普通 UI 包装。提案主动保留旧请求 writer/replay 和旧包恢复的方向正确。
- 紧凑记录能针对已证明的主要放大源，但尚无修复后数据；不能给出提速倍数，更不能仅据此承诺千万字导入或秒搜。
- 暂不建议以放弃原文独立归档来掩盖此问题。正文另存可作为独立方案，须保留版本、持久性和备份责任；直接依赖 TT 当前聊天则是另一种“宿主实时搜索”产品范围。

## 2. 证据：为什么不是仅靠换数据库或扩大缓存

固定 `evals/manual-search-demo/0.1.1-synthetic-cost.json`：

| 项目 | 记录值 |
| --- | ---: |
| 输入 | 27 条、8927 字符；提案注明无摘要/Swipe |
| io.get | 80,315 |
| io.put | 31,258 |
| 物理节点 | 31,248 |
| directory.persisted | 23,566（约占 put 数的 75.4%） |
| io.flush | 22 |
| Node Map 测量整轮 | 21.986 秒 |
| prepare.compile 累计 | 14.566 秒 |

这是 Node Map IO 及其逻辑 IO 计数，不是设备磁盘操作数、手机时延或 TT 原生基准。手机约 9000 字两三分钟是用户报告，不能与上述耗时当成同一运行。目录 candidate 的 bytes 也不等于最终物理文件大小。即使没有真实磁盘，此合成路径仍有显著计算成本；没有依据把所有耗时归咎于设备、原生 flush 或 Rust。

源码对应：
- `packages/storage/paged-json.mjs`：对象逐键递归、标量独立页，长字符串分片；没有小记录整体编码。
- `packages/storage/pages.mjs`：8192 字节页上限，map 为一个键值一页的不可变 AVL；每次路径更新/旋转会生成候选页，未命中缓存还需读取验证碰撞。
- `packages/storage/paged-coordinator.mjs`：TrackedPages 再将业务页登记到目录；当前有批量合并，但不能消除上游已制造的大量碎页。

因此本轮不是将可靠性要求删掉，而是降低单位逻辑记录带来的物理工作。之前的受控正确性验收仍可引用，但不能替代日常使用可接受性；9千字导入过慢本身就是当前 Demo 的阻塞，而不是只能延到规模评测的优化。

## 3. 与现有规划的关系及必须补齐的条件

### 3.1 不改变的领域语义

原文内容、Message/Revision/Story/Branch ID、分叉固定历史、旧版本保留、来源指纹、selection/correction、原操作幂等结果和人工确认都保持。不能靠降低 syncMode、减少必要落盘边界、覆盖旧页或删除历史提速。

紧凑对象的范围必须明确：可有界处理的消息/修订、桥接资料/映射/回执及请求材料可使用新编码；全局表、增长中的 selections/corrections、历史顺序/成员索引、累计 command.entries 等不得因此退化成每次全量重写的大 JSON。长字符串/正文块保持独立，不能因修改元数据复制其他消息的全文。不要把“整条记录”理解为“整份聊天/全库”。

8192 字节限制要计入最终序列化封装、键与转义开销；不能仅按原始字符串字符数切片。所有 read/field/set/token、恢复审计必须识别明确的编码标签，不把内嵌普通业务对象误当物理引用。字段只读访问不得为了返回一个引用而偷偷写页。

### 3.2 请求级编码策略，而非全局替换 writer

`paged-recovery.mjs::auditPaged` 重放持久请求并比较 `compiled.domain === r.after` 的精确引用关系（以 equal 实现），不只是比较用户可见文本。所以改 writer 可能使旧请求恢复失败。

提案的独立新请求 kind 或显式版本可行，但版本必须覆盖整个实际编译/持久化路径：领域记录、bridge 记录、input/generated/result 材料及相关 replay；不能只给 API 名称加版本而共用一个会改变旧输出的全局 writer。读旧写旧重放保持确定性，新请求可基于含旧页的 domain 增量生成新页。

同时检查 `Importer.recoverPending()` 等只接受 kind=bridge 的调用侧，允许按原版本处理旧请求并正确识别新 kind。未知版本明确拒绝，不自动降级。保存原 operation ID、已生成 ID 和结果，不能重新编译成一项“等价的新请求”替代待处理操作。

### 3.3 根格式升级必须覆盖 prepare，而不只覆盖 execute

当前 `#prepare` 会将 input、generated、result 和 after-domain 引用持久化，再发布含 pending 的 checkpoint。**新编码材料第一次进入已发布 checkpoint 可达集合时，根格式必须一并升级；在正常新编码请求中，这个边界通常就是 prepare 的发布。** 不能等业务 Head 正式改变或 execute 完成才升级，否则旧读者会接受一个含新编码 pending 的 v1 根。

纯校验/编译拒绝不升级活动根。升级后已确认数据、未知写入结果及原请求恢复沿原发布规则处理。根、导出 metadata、staging/激活、diagnostics 都报告实际版本。这里的存储根 v2 不等于此前已存在的逻辑包 format_version=2，命名和说明须区别。

### 3.4 旧库、备份与回退

默认只降低新增操作的写入成本，不重编码已有历史。已有碎页和旧请求仍保留；升级不会自动让旧库变小，原样导出/恢复也不能当作逻辑压缩迁移。

升级前须有可用完整备份/保全路径。当前工作台导出为 16 MiB 有界 Blob；若膨胀旧库已超限，不能只写“先点备份按钮”就继续升级。应暂停真实库升级，提供经核对的完整保存路径；或者经用户明确同意在另一个空目标重新导入，原库保留。后者不等于原全部历史/操作账本的无损迁移。

首次 v2 发布后，旧 0.1.2 不能继续写同库。回退旧代码应恢复升级前包到另一空目标并说明会缺少升级后的数据；新版本仍需读取/恢复 v1 及混合材料。自动维护门禁不改变。实施和针对性验证可以沿既有授权推进，但本回审不等于用户同意对其真实库静默升级。

## 4. 千万字：本提案没有解决的三个独立入口

### A. 导入读入/预览

`packages/bridge/source.mjs::snapshot` 先 clone 全部 messages/assets/report、canonicalize，再限制整个输入为 32 MiB；`capture` 也处理当前完整聊天数组。`Importer.preview` 还会保存完整输入及旧映射材料。

按常见汉字每字 3 字节 UTF-8 粗算，3000万字正文约 9000万字节（约85.8 MiB），尚未计摘要/候选/JSON及运行时副本，明确超出该输入限制。1000万字纯正文约30MB，加入其他材料也可能超限。紧凑持久页不会改变入口的全量复制和限制。

长期目标应是有界源分页/流式导入、稳定的来源版本/分批校验与可恢复进度，不是直接把 32 MiB 调大。需要区分许多短消息和少数超长消息：前者考验索引/目录每记录开销，后者考验文本分块/读取预算。

### B. 搜索

`packages/workbench/service.mjs::next` 目前按 snapshot 逐条读 revision、规范化后 includes；有界分批可以避免一次卡死，但不会让完整查找与总量无关。紧凑记录可降低读取常数，不能把扫描变成索引查找。

“千万字快速精确手搜”应单独落实可重建的字面/子串候选索引、精确原文复核，以及 Story/Branch/Revision/快照可见性过滤。无需先实现向量、自动摘要或模型调用，也不能把 BM25 TopK 当成完整字面搜索。长正文跨存储块匹配需保持单条消息的正确语义；短词/单字、全半角/大小写/空白规则要有明确处理。

### C. 完整导出/恢复

16 MiB 下载上限是当前 UI 资源保护；不是存储容量证明。千万字须有流式或有界分卷的完整备份交付路径。恢复当前会对全部请求做确定性重放审计，也要单独评估总工作；不能以普通重开只读 checkpoint 的速度代替完整恢复速度。

这些是长档案端到端能力的缺口，不需要立刻展开巨型性能测试，但必须在承诺规模前解决。

## 5. 正文是否可以放在别处

| 方案 | 本轮判断 |
| --- | --- |
| 同一 TT DB，紧凑记录+正文块；以后增加独立索引 | 当前最小修改，优先建议；尚未证明规模上限 |
| Mnemosyne 自有正文对象/文件/专用数据库，元数据保留引用 | 架构可行，仍属于正文独立归档。须明确持久文本版本、先存正文再发布引用、完整备份/恢复与删除责任；不是只换一个路径 |
| 正文只留 TT，扩展搜索宿主当前聊天，仅另存摘要 | 可作显式宿主实时搜索模式，但失去独立旧版本/删除前正文、离线完整档案和跨平台自足恢复的承诺。不得静默替换现有档案模式 |

固定 TT 367b0c7 的 `docs/API/Chat.md` 已提供 `history.*`、`searchMessages()` 和 `store.*`。原生搜索说明是 CJK bigram/片段评分 TopK、scanLimit 限制，不等价于完整精确子串搜索，不证明千万字秒搜；当前手机安装版的对应行为本轮未实测。`store.*` 可存每聊天独立 JSON，但仅有这些方法名不能推定具备所需事务、分块、原子发布和恢复保证。

固定 `docs/API/Database.md` 有 `indexText/indexKeyword/buildTextIndex/search`。可评估作候选索引，但文本索引未进 WAL、需要源文本可重建，且 TopK/匹配语义仍需核对。它不能替代权威正文/版本或当作完整枚举。`batchInsert` 自动分配 ID，也不是当前指定内容哈希槽位 upsert 的直接替代。

若评估 SQLite/私有文件/A服务，这是另一次 provider/部署选择，不在本次紧凑编码修改里自动实施。

## 6. 商业平台体验如何理解（外部技术背景，不是该平台实现证明）

用户未提供商业平台名称或实现资料，不能判断它使用什么数据库、是否常驻内存或哪一种索引。通用成熟做法是把正文、搜索索引、消息定位元数据分开：查询先获得候选消息ID，复核并返回少量结果，再按ID/偏移读取附近内容，而不是每次将全部正文送到前端。具体能否秒回取决于查询、索引和设备；本轮不作性能保证。

公开例子：SQLite FTS5 支持全文索引和 external-content，trigram tokenizer 支持子串候选检索，但少于三个Unicode字符的全文查询不匹配，需要短词方案，不能无条件套用。UTF-8 字节粗算依据 RFC 3629。这些只说明有成熟技术路线，不代表已在 TT 内可直接使用或已选为 Mnemosyne 后端。

## 7. 建议的下一步与测试成本

先在原提案范围内消除细粒度记录放大，不先换数据库、不丢正文、不无限增大缓存。保留提案的实现250～400行、测试100～160行估计作为预算，不作为已验证工作量；纯读字段访问或旧恢复兼容明显超范围时先回报，不牺牲正确性压行数。

有限验证由三个集合组成：
1. 旧包/旧pending按原writer恢复，新旧混合包和未知版本拒绝；特别覆盖首次紧凑prepare发布前后及execute恢复的有限故障点，不重跑旧完整强杀矩阵。
2. 小型业务用例含正文/L0/候选空位/一次编辑、一条超过页大小的文本，检查内容/ID/指纹/纯读无写及重开恢复；复用既有断言，不重复造很多变体。
3. 最终候选只复用一次原27条cost-probe，与现有基线比较逻辑get/put、持久节点和字节、编译成本；必要受影响集合一次。数量级降低是算法门槛，不是手机日用通过或千万字承诺；之后经用户许可做一次短实际导入体验核对。

若改善后仍每条消息产生极高写放大，应明确残余来源和后续结构选择，不反复用同一手机长跑或提高限制掩盖。千万字方案的源分页、全文索引和备份另外明确交付边界，不等到T-12才发现它们缺失，也不在本次自动创建/执行T-06。
