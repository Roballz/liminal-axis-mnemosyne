# v1.4.38 核心库增长与大包备份修复

日期：2026-11-15（Asia/Shanghai）

基线：`work/daily-memory-mvp-baibai` / `f8e535296f377c15fac7e5c582ae5f468ff092a2`

## 用户问题与本轮范围变化

用户更新后遇到 64 MiB 备份大小门槛，随后补充手动导出已有 270 多 MB、最长聊天 1980 楼、库内十个分支，并担心 5000 / 10000 楼持续膨胀。最初仅提高到 128 MiB 的候选没有推送；本轮转为定位并修复新增记录的额外膨胀，同时支持当前大包和本地体积诊断。

64 MiB 是插件在生成文件后、原生磁盘写入前执行的资源门槛，不是数据库损坏诊断。超过时没有生成新的磁盘恢复点，也不轮换旧文件。实际 270 多 MB 的构成没有直接读取，不能把合成模型当作用户数据库统计。

## 两项已复现的增长缺陷

1. 混合 L0 / L1 / L2 每次追加 L0，会使旧实现中全部高层 rank 增加，导致很多未改内容的叶桶重新写入并被历史视图长期保留。新稳定稀疏整数 rank 只为新增或实际重排成员分配编号；保持 schema 2、原枚举顺序和全部旧节点。常规 1 万楼混合追加的旧成员 rank 改动为零。
2. 分支复制共享旧依赖时，在异步读取之前检查去重、读取后不复核，多个路径可重复复制同一旧节点。实际 `forkBranch()` 回归中，8 层共享 DAG 原应复制 33 条，旧实现写了 527 条；修复后回到 33 条。读取后复查并在递归前预留身份，摘要与表格复用已复制的历史 ID；父分支、基线和原证据保留，失败整体回滚。

同一生产 `publishMemoryView()` 合成模型，每 2 楼一条 L0，每 8 条 L0 一条 L1，每 5 条 L1 一条 L2；仅统计所有历史视图和索引节点的累计 JSON UTF-8 大小：

| 楼层 | 修复前 | 修复后 |
| ---: | ---: | ---: |
| 1,000 | 13.41 MiB | 1.73 MiB |
| 1,980 | 49.80 MiB | 4.65 MiB |
| 5,000 | 296.70 MiB | 9.53 MiB |
| 10,000 | 1,290.73 MiB | 19.94 MiB |

1 万楼累计节点 914,809 → 15,614，最后一次新增节点 262 → 6、叶条目写入 5,523 → 66。新旧长测各在 110 秒预算内完成；假事务仅清理工作缓存，累计体积不扣除历史。原始对照在 `evals/core-package-growth-1.4.38.json`，可复现脚本为 `scripts/benchmark-summary-growth.cjs`。这些不是完整核心包体积、手机耗时或用户库实测。

## 当前容量与内存处理

- 保存、读取、预览元数据和文件导入统一支持到 512 MiB，覆盖用户报告的 270 多 MB。文件上限包含相应封装，错误报告实际 MiB 和字节数；超限仍在写入、轮换或创建恢复库之前拒绝。
- 手动导出可保留更大副本，UI 显示实际大小及当前版本能否重新导入。UI 只读 `Blob.size`，不解析完整包。
- UTF-8 字节计数采用常量内存，避免只为计数分配整包编码数组。通用 JSON 默认仍为 64 MiB，重复键、数值、深度及领域校验不放宽。
- 保存分为准备与发布两个作用域，完整包对象不再显式跨越读回阶段；固定副本同样处理。
- 恢复先完整校验原版本及 checksum，再完整校验规范化的当前 v16 引用视图。写后在同一个只读事务中，逐行精确比较 JSON、顺序和数量，避免再次读取第二份全库对象及两份全库数据哈希缓冲；失败不启用新库。
- 没有 DB 或核心包格式迁移，仍为 DB5 / v16。旧包可读；超过 64 MiB 的文件需由提高容量后的版本读取。旧历史没有自动删除或缩小。

## 本地体积诊断

新增“档案 / 迁移 → 数据包边界与恢复 → 分析核心包体积”。只在手动触发时于 Worker 分 store、每批最多 128 行读取；批间结束事务并让出执行机会，不锁住全库做长时间扫描，不新增轮询。

输出各类记录数和 JSON 字节数，以及旧完整视图、选择节点条目、审核来源、摘要依赖、旧版全文和快照引用的数量与大小。复制报告仅含固定类别与数字，不含正文、摘要内容、档案名或身份 ID。诊断带时间，检测到页面或公开归档版本变化时取消，不作为备份一致性或删除依据。

## 大包合成与失败记录

脚本 `scripts/benchmark-backup-size.cjs` 在真实 Node worker_threads 内生成合成库，调用生产保存、严格读回、磁盘恢复和实际 Worker 文件导入入口；仅模拟 IndexedDB、磁盘及 guard 传输。不访问用户资料、不强制 GC、不在脚本中提高 Node 堆限。

早期 72 MiB 候选完整往返通过（75,520,052 字节原始包），保存并读回 6.87 秒，10ms 主线程 heartbeat 最大间隔 22.4ms，无超过 50ms；整进程采样 RSS 峰值约 1.49 GiB。该候选早于本轮后续增长和恢复优化，不能冒称最终版本的 270 MB 验证。

288 MiB 首次探针保存和读回成功（38.36 秒），随后恢复触及默认 Node 堆上限 2,348,810,240 字节而失败，整进程采样 RSS 峰值 4,519,895,040 字节。失败记录原样保留。随后确认探针的已关闭 fake IndexedDB 连接仍被 `const lib` 强持，`CoreBackups.running` 的完成 Promise 也保活恢复 Library；这与原生 IndexedDB 连接不在 JS 中存整库不同。探针在关闭并删除自己的 fake 库后清除这些外部引用，不改 fake 内部结构、不强制 GC、不提高内存上限；因此复测有具体失败依据，仅排除探针额外保活的数据副本。

## 最终大包结果

最终候选复测通过，原始输出和首次失败一起保存在 `evals/core-backup-288m-1.4.38.json`。

- 原始核心包 302,071,625 字节（288.08 MiB），备份文件 302,071,943 字节。实际写入、严格读回、独立新库恢复、再次导出核对，以及实际 `core-backup.worker.ts` 原始文件导入后再次导出核对全部通过。
- 保存并读回 31.06 秒；磁盘恢复 28.34 秒；原始文件经生产 Worker 入口导入 16.14 秒。包括合成库生成、额外两次导出核对和释放测试库，总计 122.28 秒，在 290 秒预算内结束。
- 10ms 主线程 heartbeat 共 12,040 次，最大间隔 55.6ms，超过 50ms 一次。这只表明本机 Node 主线程未被备份计算持续占住，不代表浏览器绘制或手机零卡顿。
- 默认 Worker 堆限仍为 2,348,810,240 字节，阶段边界采样堆使用峰值 1,826,596,344 字节（约 1.70 GiB）；整进程每 100ms 采样 RSS 峰值 4,522,352,640 字节（约 4.21 GiB）。RSS 包含 Node、内存 fake IndexedDB、文件 Blob 和测试比较副本，不能当作手机所需内存，也不能忽略大包的内存风险；采样还可能漏掉短峰值。
- 实际磁盘模拟调用为写 1 次、读 2 次、删 0 次；保存与恢复均读取持久化文件，没有用仅检查 Blob 大小代替读回验证。未强制 GC，未自定堆限；测试生成的源 fake 库在恢复前释放。

## 未验证与后续边界

- 没有运行用户真实数据库、TT 原生 Blob 传输、Android 低内存/低空间、真实 512 MiB 顶格包或 20 份大包轮换。此前 Chromium 的 IPC 启动限制未改变，没有重复该受阻实验。
- 完整包仍有对象、序列化、哈希与文件读回成本，Worker 不消除应用整体内存压力。20 份都达到 512 MiB 时文件本身约 10 GiB；用户当前 270 多 MB 的 20 份也会占用约 5–6 GB，手动和固定副本另计。
- 旧版全量映射、已经写入的重复节点和历史副本仍保留；未启用高层总结时的依赖列表、逐条前缀审核也可能增加体积。需要体积报告才能判断用户已有大包的主要来源，不能盲删记录。
- 进一步无损整理应在独立新库验证历史视图、引用和顺序等价后再切换，并保留原库。本次没有自动迁移或清理旧历史，也没有把有限门槛宣称为无限容量。

## 实际改动、回退与下游依赖

共 34 个文件：14 个产品源码文件新增 417 行、删除 44 行；8 个测试文件新增 493 行、删除 2 行；2 个合成基准脚本新增 347 行。其余为 2 个构建产物，以及 8 个版本、说明和结果文件。范围由初始容量门槛扩展为增长修复和诊断，是用户补充实际 270 多 MB 与长期楼层需求后做出的调整。

本轮未操作真实用户数据库，未删除或压缩历史，未改变 DB5 / 核心包 v16 协议。更新后新写入采用稳定 rank 与依赖去重，旧节点仍可按原路径读取。回退到基线代码不需要逆向数据迁移，但会重新遇到 64 MiB 备份门槛，并失去新写入的增长修复；已经导出的较大文件应保留，由支持相应容量的版本读取。

下游现场验收：更新插件后手动保存一次并确认出现新的成功时间，再执行“分析核心包体积 → 复制体积统计”。这份只含数字的报告决定是否需要对既有 270 多 MB 做独立、可验证的历史存储整理；本次不提前把该库判定为已瘦身或手机体验已验收。
