## Query 宿主转发与参数保真

- Query 不再从 WebView 直连供应商，改为请求宿主 `/api/backends/chat-completions/generate`，`chat_completion_source: custom`、`custom_api_format: openai_compat`、`type: quiet`。不用 `generateRaw` 或主 API 预设，不获取主生成全局锁，不新增串行排队；不改摘要、Embedding、Rerank 的网络代码。
- `getRequestHeaders()` 提供宿主请求头 / CSRF。上游鉴权通过 JSON 字符串形式的 `custom_include_headers` 明确给定，包括空 key，防止误用宿主另存的 Custom 密钥。没有保存、读取或重置宿主密钥。
- URL 保留原 Query 规则：去尾斜杠和 `/embeddings`、`/chat/completions` 后缀，由宿主追加端点，不给裸域名自动加 `/v1`。用户的 `/merge/v1` 路径不变。模型、URL、key、最大 token 仍来自原 Query 设置，原本留空复用 Embedding URL/key 的规则不变。
- 温度 0.1、top_p 0.8、max_tokens、stream false、enable_thinking false 同时进入最终 `custom_include_body`，防止宿主字段筛选静默丢失。TT 对 DeepSeek v4 会按模型名添加 `thinking: {type: enabled}`，故最终 `custom_exclude_body` 仅删除 `thinking`，不换成新的 disabled 协议。上游保留旧 Query 参数，而不是让宿主改其思考机制。
- 固定 TT 提交 `007abf7f1edfff275cf2a0182bf19179bcef087a` 源码表明 Custom 默认不做消息后处理或自动缓存控制；模型 / 消息走原字段，避免重复复制大上下文。当前纯文本非流式、无工具的 DeepSeek Query 场景最终有效 payload 与旧直连一致。其他宿主版本或其 text-completion 特殊模型并未宣称逐项实机验证。
- 复用同一个 `fetchWithTimeoutRetry`，保留每次尝试独立 controller、Query 自己的超时 / 次数、800 ms 退避、完整响应体超时、外部取消不重试。失败后不回退 WebView 直连，不调用全局停止 API。额外对无效 JSON 和宿主 error 对象明确报错，仍不降级继续召回。

## 已知宿主边界

摘要原本通过宿主转发，而旧 Query 是 WebView 直连，后者受到 CORS / WebView 网络策略等额外约束。用户反馈本机 gproxy 摘要成功、Query 快速 Failed to fetch，去掉 /v1 也失败；本轮按授权切换路径，不把未取得的 Network/OPTIONS 现场证据冒充已证实的具体根因。没有发送真实 API 请求、读取密钥或提交私人 RP。

TT `quiet` 路径不会把错误伪装成生成成功，但其原生失败会包装为 HTTP 502，结构中不可靠保留原始上游 HTTP 状态。因此现有重试策略看到宿主 502 会按所配置次数重试，即便最初供应商返回 400；不靠解析错误文案猜测状态。直接可读的宿主 400/401/403 仍不重试，取消绝不重试。该限制需要用户知悉，不能声称上游 4xx 的零重试语义完全等价。
